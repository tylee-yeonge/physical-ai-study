## 0. TL;DR

- **VLA 학습 가능 여부**: 가능. 단 로컬 4070 단독으로는 불가하고, 레포는 이미 RunPod 분업 전제로 설계돼 있다. 사양 부족은 계획을 막는 요소가 아니다.
- **이직 가능 여부**: 이 공부"만"으로 이직하는 것이 아니다. 뽑히게 만드는 것은 양산 AMR ROS 5년이고, 공부는 지원 가능한 직무의 범위를 바꾸는 역할이다.
- **최종 포지셔닝**: 코어 = 로봇 시스템 SW 통합 / 엣지 = Physical AI(VLA) 준비된 사람. "VLA 통합 엔지니어"라는 직함은 시장에 그대로 존재하지 않으므로 지원 시 각 회사 JD 언어로 번역한다.
- **실체 인정**: rclpy 중심 5년 + C++ 코어·DDS 내부 깊이 부족. 진짜 자산은 스택 깊이가 아니라 양산 시스템 운영 경험이다. 이를 전제로 gap 방어 전략을 짠다.
- **스택 gap은 면접 방어용이지 서류 돌파용이 아니다.** 서류를 통과시키는 물건은 Phase 4.5 산출물(돌아가는 파이프라인 + 정량 분석)이며, 전달 채널은 vla-lab(공개 산출물 repo)이다 — 이 레포는 비공개라 직접 보이지 않는다.

## 1. VLA 학습 실행 가능성 판정 (레포 기준)

### 1.1 결론

"**가능하지만 로컬 단독으로는 불가**"이며, 레포 문서들이 이미 그 전제로 설계돼 있다. PC 사양 부족은 사실이나, 한 달 전 `docs/research/isaac-sim-so101-course.md` §5에서 계산이 끝난 사안이다.

### 1.2 학습 종류별 판정

| 학습 종류 | 로컬 4070 12GB | 판정 근거 및 경로 |
|---|---|---|
| OpenVLA 7B LoRA (Phase 4.5) | 불가 | 24GB+ 필요. RunPod RTX 4090 (24GB) 학습 → 로컬 머지 + 4-bit 양자화 (~6GB) → 로컬 추론·eval. 문서에 분업 확정됨 |
| GR00T post-training (NVIDIA SO-101 코스) | 불가 | 기본 ~25GB. 4090 24GB에서도 `--no-tune_diffusion_model` / `--lora-rank` 축소 플래그 필요. RunPod 전제 |
| ACT (LeRobot, SO-101 teleop 데이터) | **가능** | 소형 모델. Stage 1 체크리스트 "ACT 1회 학습"은 로컬 정석 경로 |
| SO-101 teleop / 데이터 수집 | 사양 무관 | GPU 부담 거의 없음. USB 물리 접근이 조건이며 2026.09 자택 이전으로 충족 |

### 1.3 진짜 리스크: 학습이 아니라 sim

- Phase 4.5 sim은 ManiSkill이라 4070으로 충분. 문제는 **Isaac Sim** — 최소 사양 (VRAM 16GB / RAM 32GB) 대비 보유 12GB / 31GB로 미달, GUI는 UDP 47998 요구로 RunPod 이관 불가.
- 단 Stage 1의 단일 팔 URDF 임포트는 가장 가벼운 축이라 로컬 가능 전망. 실패 시 해당 항목만 Phase 6로 이월하는 분기가 이미 문서화돼 있다.
- GPU 증설(5070 Ti 16GB, 139-208만원)은 보류가 맞다 — Isaac Sim 미달만 해소하고 LoRA 24GB 벽은 못 넘어 RunPod 의존이 그대로다. 학습은 회당 1-2.5만원 수준의 RunPod가 비용상 압도적으로 합리적.

### 1.4 미검증 항목

1. 워크숍 docker의 RunPod headless 이식 실제 난이도 (Phase A에서 처음 부딪힘)
2. 4090에서 GR00T 축소 설정의 성능 손실 (커뮤니티 보고 수준)
3. **Section 0 잔여 실측**: RunPod LoRA 1사이클 (시간/비용/체크포인트) + fine-tuned 4-bit이 4070 12GB에 OOM 없이 올라가는지 — 마감은 달력(8월)이 아니라 **week3 (LoRA 본 학습) 진입 전**이다 (학습 데이터가 Section 1 산출이라 8월에 닫을 수 없음, remediation plan 실행 보드 #6)

Section 0 전반 — sim 구축 + 하네스 검증 + zero-shot baseline — 은 측정 완료 상태다 (2026-08-03, `Measurements/openvla-maniskill-zeroshot/`). 지금 필요한 것은 사양 걱정이 아니라 위 잔여 실측으로 판정 검증을 마저 닫는 것이다.

## 2. 이직 가능성 판정

### 2.1 구조 이해

이 공부만으로 이직하는 것이 아니다.

- **뽑게 만드는 것**: 양산 AMR ROS 5년 (멀티 앱 아키텍처 설계, 현장 장애 대응, 배포 운영)
- **공부의 역할**: 지원 가능한 직무의 범위를 넓히는 것 — "또 하나의 AMR SI 자리"가 아니라 Physical AI 팀에 지원할 자격을 만드는 것

### 2.2 되는 시나리오

Physical AI 팀의 **통합/미들웨어/배포 엔지니어**.

- VLA 연구자 자리는 ML 박사들이 채우지만, 모델을 실기에 얹고, latency를 재고, 안전 인터록을 만들고, ROS2로 시스템을 짜는 사람은 따로 필요하다.
- 양산 ROS 5년 + "OpenVLA를 직접 돌리고 LoRA 파이프라인을 설계-실행-정량분석한 사람"의 조합은 국내에서 희소하다.
- 레포의 문서화 방식 자체 — 측정 방법론 (N, 분산, 부분 도달률), 제약 계산 (RunPod 분업, 사양 판정) — 이 시니어 엔지니어링 판단으로 읽히며, 튜토리얼 추종 포트폴리오와 구별된다. 단 이 레포는 비공개이므로 채용 측에 실제로 보이는 것은 **vla-lab (공개 산출물 repo) 발행물** — 실측 write-up + v1.5 문서 — 이다. 문서화 방식의 어필은 그 발행물이 담당한다.

### 2.3 안 되는 시나리오

**"VLA 연구/모델 개발" JD.**

- 논문 없음, 대규모 학습 경험 없음, sim-only 증거의 한계는 스터디 몇 달로 메워지지 않는다.
- 여기 지원해서 서류에서 떨어지는 것은 정상이며, 공부량 부족이 아니라 포지셔닝 오류다.
- 모델 개발 직군 직행의 격차는 몇 달이 아니라 몇 년 단위이고, 그동안 소득과 시간을 태워야 한다. 팀 진입 후 내부에서 데이터 파이프라인 / eval / fine-tuning 운영으로 역할을 넓히는 경로가 훨씬 빠르다.

### 2.4 리스크 3가지

1. **독학 포트폴리오는 면접에서 깊이 검증을 당한다.** "왜 4-bit이고 8-bit이 아닌가" 수준의 질문에 막히면 오히려 감점. 산출물마다 결정 근거를 말로 설명할 수 있어야 한다.
2. **휴직 중 이직 시도.** 복직 카드가 있어 리스크는 낮은 편이나 공백기 질문 준비 필요.
3. **타깃사들이 실제로 "통합 엔지니어" JD를 내는지는 아직 가설.** 측정 장치는 2026.11 분기 재평가 #1이다 — 휴직 중 구직 지원 금지 원칙(정찰 포함)에 따라 JD 정독 5-10건 + probe 반응(LinkedIn 헤드라인·커피챗)으로 검증한다. 서류 통과율은 재평가에서 조기 지원(2027.01)이 결정되면 그때, 아니면 복직(2027.03) 후 실지원에서 확보한다.

"이 정도로 될까"는 지금 걱정할 질문이 아니라 11월 재평가에서 데이터로 확인할 질문이다.

## 3. 최종 포지셔닝 정의

### 3.1 정체성 문장

> **"AI 모델(VLA 포함)을 실물 로봇 시스템에 통합·배포·운영하는 엔지니어"**
> 근거: 양산 ROS 5년 + Physical AI 파이프라인 실증

### 3.2 코어 / 엣지 구조

| 층 | 내용 | 역할 |
|---|---|---|
| **코어** | 로봇 시스템 SW 통합 (ROS2 아키텍처, 배포, 운영) | 어디서나 팔리는 것. 회사가 VLA를 안 해도 지원 가능 |
| **엣지** | Physical AI / VLA 준비된 사람 (OpenVLA 배포, LoRA 파이프라인, sim eval) | 다른 ROS 5년차와 구별해주는 상단 레이어. 회사가 VLA를 하면 특히 강한 후보 |

### 3.3 왜 VLA로 좁히지 않는가

- "VLA 통합 SW 엔지니어"라는 직함은 시장에 그대로 존재하지 않는다. 실제 JD 명칭은 Robotics Software Engineer / Robot Application Engineer / System Integration Engineer / AI Deployment Engineer 등으로 흩어져 있다.
- 2026년 시점 국내에서 VLA를 실제 제품에 넣는 회사는 소수이고, 타깃사 상당수는 전통 매니퓰레이션 + 비전 단계다. "VLA 통합"만 목표로 박으면 지원 풀이 과도하게 좁아진다.
- 지원 시 번역 예: 매니퓰레이션 FM → 비전-로봇 통합, 협동로봇 중심 대기업 → 로봇 SW 플랫폼.

### 3.4 "결국 미들웨어"에 대한 관점

- 입구는 미들웨어가 맞다. 그러나 두 가지를 구분한다.
- **같은 직무명이라도 층이 다르다**: 현재는 확정된 스택 위의 SI 미들웨어. Physical AI 통합은 모델의 불확실성을 다루는 일 — 추론 latency와 제어 주기의 충돌, VLA 출력의 안전 게이팅, sim-to-real 배포. 업계에 정답이 없는 문제라 경험의 시장 가치가 다르다. "미들웨어를 계속 한다"가 아니라 "미들웨어 스킬로 문제 도메인을 갈아탄다".
- **입구가 종착점이 아니다**: 로드맵의 3-Layer 구분 그대로 — 셋째 층(배포·통합)으로 진입하고 둘째 층(adaptation) 증거를 Phase 4.5로 쌓는다. 팀 내부에서 역할이 번지는 것이 밖에서 스터디로 뚫는 것보다 빠르다.

## 4. 기술 스택 전체 목록 (VLA 외 일반 요구 사항)

로보틱스 시스템 SW / 미들웨어 엔지니어 JD 기준. 각 항목을 O(설명 가능) / △(써봤으나 설명 약함) / X(경험 없음)로 자가 진단할 것.

### 4.1 C++ (가장 자주, 가장 깊게 검증됨)

- Modern C++ (14/17/20): RAII, 스마트 포인터, move semantics, 템플릿 기초, STL 컨테이너 시간복잡도
- 동시성: `std::thread`, mutex / condition_variable, atomic, 데드락·race 디버깅, lock-free 개념
- 메모리 모델: 스택/힙, 캐시 친화성, 실시간 루프에서 동적 할당을 피하는 이유
- 검증 패턴: "ROS 5년인데 C++ 깊이는?" — rclcpp 사용 수준과 언어 자체 깊이는 다르게 평가됨

### 4.2 Linux 시스템 프로그래밍

- 프로세스/스레드 모델, 스케줄링 정책 (SCHED_FIFO/RR, nice), CPU affinity
- IPC: shared memory, socket, pipe — DDS가 내부에서 무엇을 쓰는지 설명 가능한 수준
- PREEMPT_RT, 지연 원인 분석 (페이지 폴트, 우선순위 역전), cyclictest 류 도구
- systemd 서비스 작성, udev 규칙, cgroup 기초

### 4.3 ROS2 내부 구조 (사용이 아니라 내부)

- Executor 모델 (single/multi-threaded, callback group), intra-process comm, composition
- DDS 계층: QoS 정책별 실제 동작 (reliability / durability / deadline / liveliness), discovery 트래픽 문제, rmw 구현체 차이 (FastDDS / CycloneDDS)
- lifecycle node, ros2_control 아키텍처 (hardware_interface / controller)
- TF2, 시간 동기 (sim time, PTP 개념)
- 5년 실무 영역이므로 "QoS 잘못 잡아서 겪은 장애" 같은 실전 서사로 승화시켜야 하는 영역

### 4.4 네트워크 / 통신

- TCP vs UDP 트레이드오프, 직렬화 (CDR, protobuf), 대역폭 계산 (카메라 토픽이 터지는 이유)
- 필드버스: CAN (보유), EtherCAT / Modbus는 개념 수준
- zero-copy, 메시지 크기와 latency 관계

### 4.5 빌드 / 툴체인 / 디버깅

- CMake 제대로 (target 기반, 의존성 관리), colcon, 크로스 컴파일 (Jetson aarch64)
- gdb (코어 덤프 분석), valgrind / ASan / TSan, perf / flamegraph 병목 분석
- "미들웨어 개발자"와 "ROS 사용자"를 가르는 실질 경계선

### 4.6 테스트 / CI

- gtest / pytest, 통합 테스트 설계, GitHub Actions 등 CI 파이프라인 구축
- clang-tidy / clang-format 정적 분석, 코드 리뷰 문화 경험

### 4.7 배포 / 운영 (양산 경험자에게 특히 기대)

- Docker: 멀티스테이지 빌드, GPU/장치 패스스루, compose (보유)
- 로깅/모니터링 설계, 원격 진단, OTA 업데이트 개념
- rosbag / MCAP 기반 필드 데이터 회수·재현 파이프라인

### 4.8 안전 / 신뢰성 (Physical AI 통합 차별화 포인트)

- watchdog, e-stop 채널 분리, fault handling 상태기계, graceful degradation
- behavior tree 또는 상태기계 프레임워크 사용 경험
- 기능안전 (ISO 13849 등)은 인지 수준이면 충분

### 4.9 엣지 / 가속 (타깃 직무 특화)

- CUDA 기초 (커널 작성까지 불요, 메모리 전송 병목 이해), TensorRT 빌드·양자화 — Phase 3-4로 확보 중
- Jetson 플랫폼 특성 (JetPack, 전력 모드, 통합 메모리)

## 5. 현재 상태 인정과 Gap 분석

### 5.1 실체 (스스로 인정한 것)

- rclpy 중심 5년. C++ 코어 깊이 부족
- 디버깅은 Python 방식 (pdb, 로깅, py-spy 류) 중심
- DDS 등 ROS 하부 기술을 깊게 파면 잘 모름

### 5.2 재정의: 진짜 자산

기술 스택의 깊이가 아니라 **양산 시스템을 5년 굴린 경험** — 멀티 앱 아키텍처 설계, 현장 장애 대응, 배포 운영. 책으로 못 배우는 것이라 여전히 유효한 카드다. 단 "미들웨어 코어를 아는 사람"으로 포장하면 면접에서 무너지므로 그렇게 팔지 않는다.

### 5.3 관점: 전 영역 만점은 요구되지 않는다

- 목록 전부를 깊게 아는 사람은 거의 없고, JD가 다 나열해도 실제 검증은 두세 영역에서만 이뤄진다.
- 채용 측이 보는 것은 "깊은 축 하나 + 나머지는 부딪히면 파고들 수 있다는 증거"다.
- 따라서 전략은 gap 전부 메우기가 아니라 **떨어지는 지점만 방어**.

### 5.4 Gap별 대응 전략

| Gap | 리스크 | 대응 | 비용 |
|---|---|---|---|
| **C++ 깊이** | "rclcpp 5년인데 move semantics 설명 못 함" — 가장 아픈 낙방 패턴. C++ 필수 JD는 서류·코딩테스트 단계에서 걸릴 수 있음 (돌려 말할 수 없는 사실) | (1) 언어 코어만 좁게 다지기 — RAII, 스마트 포인터, 동시성. 새로 배우는 게 아니라 이미 쓰던 것을 설명 가능한 언어로 바꾸는 작업. (2) **Stage 2 안전 인터록 노드(C++)를 실증 카드로** — "성능·안전이 필요한 지점은 C++로 내려간다, 실제로 내려가봤다"는 서사. 없는 5년을 지어내는 것보다 진짜 증거 1개가 강함 | 중 |
| **DDS / ROS2 내부** | "ROS 5년"의 기대치와 실제 깊이의 괴리 | 세 gap 중 가장 메우기 쉬움 — 범위가 유한. 검증 수준: QoS 정책별 동작 차이, discovery가 노드 증가 시 터지는 이유, rmw를 바꿔 끼는 이유, 대역폭 큰 토픽의 병목. 집중 2-3주면 "설명 가능" 도달. **지렛대**: 5년치 현장 경험 — 원리를 채우는 순간 기존 경험이 소급해서 깊이 있는 서사로 바뀜. 제로에서 배우는 사람과 효율이 다름 | 저 |
| **디버깅 도구** | "C++ 노드가 죽으면 어떻게 잡을 건가"에 답이 없음 | Python 방식 자체는 정당. gdb 코어 덤프 + sanitizer를 인터록 노드 제작 시 함께 사용 — 각각 1-2일 투자로 "써봤다" 확보, 그것으로 충분 | 저 |

### 5.5 rclpy의 재해석 (약점 → 정합)

- 시스템/미들웨어 코어 개발 JD에서는 약점이 맞다. 당분간 승률이 낮음을 인정한다.
- 그러나 타깃인 **VLA 통합 직무에서는 정합**이다 — LeRobot·학습·eval 스택이 전부 Python. rclpy 5년이 자연스럽게 이어진다.
- 아키텍처 설계, QoS/executor 판단, 장애 대응 서사는 언어와 무관하게 성립한다.
- 실제 강점의 정확한 명칭: "고성능 미들웨어 코어 개발"이 아니라 **"애플리케이션/통합 계층 설계와 양산 운영"**.

## 6. 우선순위와 실행 계획

### 6.1 우선순위 원칙

1. **Phase 4.5 진행이 모든 스택 공부에 앞선다.** 서류를 통과시키는 것은 완벽한 미들웨어 지식이 아니라 "돌아가는 파이프라인 + 정량 분석"이고, 그것이 외부에 보이는 채널은 vla-lab 발행물이다.
2. 스택 gap 대응은 면접 방어용 — 별도 공부 트랙을 새로 열지 않고, 로드맵 진행 중 자연 커버 + 좁은 집중으로 처리한다.
3. 로드맵 자연 커버 범위: 스파이크·Stage 1이 ros2_control·udev·크로스 컴파일을, Phase 4.5 컨테이너화가 Docker·CI 서사를 만든다. 진행하면서 "면접에서 말할 수 있는 형태로 기록"하는 습관만 추가한다.

### 6.2 스택 gap 트랙 배치 (2026.09 - 2027 상반기)

배치 원칙: 2026.09-12 는 Phase 4.5 Sections 1-3 + 스파이크 + 재평가 #1 + 정독 잔여(12월, 20-30h)로 만재라 새 트랙이 들어갈 자리가 없다 (월 예산 30-35h — year-end guide §2). 2026.12 앞당김은 검토 후 배제했다 — 12월 예산은 정독 잔여가 채우고 있고, 정독 역시 v1 완결성("아키텍처를 막힘없이 설명")을 닫는 면접 방어 항목이라 밀어낼 명분이 없다. **2027.01-02 도 만재다** — Hardware-Arm Stage 1 본 빌드(한 구간 1트랙 메인, 약 35-55h) + 초기 패키징 최소선(2-3주)이 예산(월 30-35h x 2)을 채우므로 스택 gap 트랙과는 **배타 배치**한다. 스택 gap 의 마감 기준은 달력이 아니라 **실제 검증 시점**이다 — C++ 이 실제로 걸리는 지점은 서류가 아니라 코딩테스트(지원 후 2-4주, 2027.03 말-04 초)이고, 서류 단계의 C++ 방어는 어차피 실증 카드(Stage 2 인터록, 2027.04-06) 전이라 얇다. 따라서 C++ 코어는 2027.02 말-03 에 DDS 서사화와 병합 배치한다 — 둘 다 "이미 쓰던 것의 언어화" 성격이라 병합이 자연스럽고, 면접 직전일수록 신선하다 (첫 면접은 현실적으로 2027.04 이후 — 3월 지원 + 프로세스 1개월).

### 6.3 면접 준비 체크 (2027.01-03 — 최소분은 패키징, 본문은 병합 트랙)

수행 시점은 둘로 나눈다 — 이력서에 직접 들어가는 최소분(공백기 답변 골자, 산출물별 결정 근거 요약)은 초기 패키징(2027.01-02)에 포함하고, 서사 본문(코어 서사 5개 추출 + C++ 방어)은 2027.02 말-03 의 C++·DDS 병합 트랙(§6.2) 산출물로 준비한다 — 첫 면접이 현실적으로 2027.04 이후라 시간이 맞는다. 진행 체크는 본 문서에서 하지 않는다 — 시점 도래 시 초기 패키징 체크리스트(README 마일스톤) 또는 remediation plan 실행 보드로 이관해 체크한다.

- 코어 서사: 양산 ROS 5년에서 실전 장애 대응 서사 5개 추출 (QoS, discovery, 대역폭, 배포, 장애 복구 등 — 원리 설명 포함으로 재구성)

## 7. 판단 근거 요약 (한 줄씩)

- 사양 부족 → 계획이 이미 우회 설계됨. 걱정이 아니라 실측이 필요.
- 이직 → 공부가 아니라 경력이 뽑히게 하고, 공부는 문을 넓힌다.
- 포지셔닝 → 코어(시스템 통합)로 팔고 엣지(VLA)로 구별된다.
- 미들웨어 → 입구가 맞고, 문제 도메인을 갈아타는 것이며, 종착점이 아니다.
- 스택 gap → 전부 메우지 않는다. 떨어지는 지점(C++, 디버깅)만 방어하고 DDS는 기존 경험을 서사화한다.
- rclpy → 코어 개발 JD에선 약점, VLA 통합 JD에선 정합. 인터록 노드 1개가 C++ 방어 카드.
- 모든 가설 → 1차 검증은 2026.11 재평가의 JD·probe 신호, 최종 심판은 복직 후 실지원의 서류 통과율.
- 스택 gap 배치 → 2026 년과 2027.01-02(Stage 1 본 빌드 + 패키징 최소선) 모두 만재. C++ 코어와 DDS 서사화는 2027.02 말-03 병합 배치 (C++ 실질 마감 = 코딩테스트, 2027.03 말-04 초), 디버깅 도구는 Stage 2 곁다리. 확정은 재평가 #1.

## 왜 자작 팔인가


*"Brain ↔ Body 통합 SW 엔지니어"* 의 가장 완전한 증거. 본인 약점 (VLA 신입급) 을 본인 강점 (AMR ROS 실무 5년, 2021.06~ + 펌웨어 2.5년 하드웨어 이해) 으로 직접 깨는 카드.


### 실행 품질로 증명하는 3가지

latency 측정, e-stop, BOM 이해는 로보틱스 랩에서도 일상적으로 다룬다 — 항목 자체가 희소한 것이 아니다. 차별점은 양산 ROS 5년 경험자가 이것들을 제품 수준 감각 (측정 방법론, 안전 설계 관행, 원가 구조) 으로 수행한다는 **실행 품질**이다.

- **latency**: 추론 → 모터 명령까지 ms 단위 측정
- **안전 메커니즘**: e-stop, 토크 한계, 충돌 감지 직접 구현
- **양산 비용 이해**: DIY 팔 BOM 표 — "이 가격대에 이 성능까지"


### 보너스
- **LeRobot / Hugging Face 생태계 표준 하드웨어**를 쓰므로, teleop 데이터 수집 → LeRobot 포맷 데이터셋 → ACT 학습 → HF Hub 공개 (v2.5) 경로가 그대로 이어진다. 채용 관점에서 읽히는 것은 모터 브랜드가 아니라 이 파이프라인 경험이다.
- 펌웨어 직무로 지원하지 않지만 *이해의 폭* 으로 차별화.

### 카메라 구성

팔 키트에 카메라가 없으므로 별도로 갖춘다. LeRobot 표준은 **손목 1대 + 외부 1대**다.

| 위치 | 장비 | 사양 |
|---|---|---|
| 손목 (**팔로워** 그리퍼) | 추가 구매 (1-3만원) | 소형 UVC USB 웹캠, 640x480 @ 30fps |
| 외부 (전면 또는 상단) | 보유 ELP Stereo 활용 (RGB 한쪽 스트림) | 720p-1080p @ 30fps |
| 리더 | **없음** | — |

### 작업대 자재

NVIDIA SO-101 코스의 실물 단계(Phase B)를 Stage 1 과 겹쳐 진행하므로, 그 코스의 BoM 자재(vial·랙 등 태스크 물체)를 **팔 구매 시점(2026.09)에 함께 잡는다.** 코스 요건과 두 단계 분할은 [`docs/research/isaac-sim-so101-course.md`](../docs/research/isaac-sim-so101-course.md) §4 다.

**리더에 달지 않는 이유**: 정책을 자율 실행할 때 리더는 존재하지 않는다. 카메라를 리더에 달면 데이터 수집 때와 자율 실행 때의 관측 분포가 완전히 달라져 학습이 무의미해진다. 관측 시점은 배포 시에도 존재하는 팔로워여야 한다. 부수적으로 리더는 사람이 계속 손으로 움직이는 팔이라 카메라 무게·케이블이 곧 조작 부하가 된다.

실전 주의 3가지:

- **동일 모델 2대를 쓰지 말 것** — USB 경로가 무작위로 바뀌어 5-10분마다 끊긴다. udev 규칙으로 물리 경로를 고정하거나 서로 다른 모델을 쓴다. ELP + 다른 웹캠 조합이면 자동으로 회피된다
- **배치는 전면-상단이 전면-측면보다 낫다** — 측면은 파지 중 그리퍼 팁에 가려진다. 공개 사례에서 이 조정을 포함해 성공률이 60% → 90% 로 올랐다
- **카메라를 물리적으로 고정하고 노출·화이트밸런스를 잠글 것** — 소량 (50 에피소드 급) 데이터로 학습한 모델은 시점 변화를 견디지 못한다

카메라가 실제로 필요해지는 시점은 조립·teleop 데이터 수집, 즉 스파이크·Stage 1 (2026.09-11) 이다. 다만 **팔 키트와 같이 즉시 산다** — 1-3만원이라 선집행 부담이 없고, 따로 사면 조립 직전에 누락되기 쉽다. 선행은 판매자 확인 4항목 중 #4 (3D 부품에 손목 카메라 마운트 포함 여부) 이며, 어차피 문의 -> 발주 순서라 같은 흐름에서 처리된다.


**비채택 기록**:
- **Koch v1.1** (Dynamixel 기반, ROBOTIS 국내 부품 41.3만원 + 서드파티·3D 프린팅 = 총 49-60만원): 2026-07 검토 후 비채택. 1순위 타깃사 (Dynamixel 제조사) 액추에이터 정합이라는 이점이 있었으나, 채용 관점에서 결정적인 것은 "어느 회사 모터를 썼는가" 가 아니라 "LeRobot/HF 파이프라인으로 무엇을 했는가" 라고 판단했다. 실무 요인도 SO-101 우위 — 리더 모터 XL330-M077-T 준비기간 40일 (휴일 미포함) 배송지연 vs SO-101 3일, 3D 프린팅 부품 자체 조달 필요 (외주 시 약 11만원) vs 키트 포함. LeRobot 생태계에서도 Koch 는 지원 목록에 남아 있을 뿐 현행 표준은 SO-101 이다 (SO-100 은 공식 문서상 deprecated)
- 커스텀 XL330+XM430 풀세트 (BOM 약 150-225만원): 비용 약 3-4배 + 리더-팔로워 teleop 미지원 (별도 입력 장치 필요) → 비채택
- AR4 (스테퍼 기반, 약 50-100만): 토크 피드백 없음 → "안전 메커니즘" 증거 약화 → 비채택
- "SO-101 프레임에 Dynamixel 을 얹는" 절충: 불가. 프레임 STL 이 STS3215 치수·토크 전제라 브래킷·링크 전면 재설계가 되고, 그 순간 SO-101 을 고를 이유였던 생태계 정합도 함께 소멸한다 (LeRobot 의 SO-101 설정은 Feetech 버스 전제)

## 스파이크 (2026.09 첫 2주 타임박스, 산출물 아님 = 리스크 검증)

> **실행 시기 2026.09 첫 2주로 전진** (2026-08-30 실기 전환 결정 — 구 "2026.10 확정" (2026-08-12 체크포인트) 을 대체). v1.5 실측이 선행돼 9월 트랙이 비었고 물리 접근 (자택 이전) 도 확보됐다. 절차·통과 기준·판정의 원본: 실기 전환 plan (`../docs/superpowers/plans/2026-08-30-realworld-transition-execution.md`) §5. Stage 2 확장 수단 결정은 2026.11 분기 재평가 안건으로 유지한다.


첫 하드웨어는 계획의 2-3배 걸린다. 본 빌드 (Stage 1) 전에 짧게 굴려 파이프라인을 먼저 검증한다.


- **범위**: 조립 + LeRobot 네이티브 스택 검증. ROS2/URDF/Isaac Sim/파인튜닝은 범위 밖 (ROS2 는 Stage 1 로 이동). 안 예뻐도 됨.
- **목표**: "이 환경에서 SO-101 이 LeRobot 으로 teleop 되고, 데이터가 녹화되고, 사전학습 VLA 가 팔을 움직이는가" 만 확인. pick-and-place 성공률 아님.
- **출력**: **판정 2026-09-21 1회** — must 통과 시 Stage 1 2026.10 개시 / teleop 불가 또는 2주 초과 시 원안 일정 (10월 스파이크·12월 빌드) 롤백. 분기 재평가 #1 (2026.11) 입력.


키트 도착 후 조립을 마치고, ROS2 층 없이 LeRobot 네이티브 명령만으로 실기 경로 전체 (teleop → 녹화 → 정책 실행) 를 확인한다. 주차별 진행표는 실기 전환 plan §5.3.

통과 기준 (must 4 — 실기 전환 plan §5.2):

1. 리더-팔로워 teleop 동작 (`lerobot-teleoperate`, 6축 추종) — 30초 영상
2. `lerobot-record` 로 단일 task 10 에피소드 녹화 + HF Hub (private) 업로드 — 데이터셋 repo id
3. `lerobot/smolvla_base` zero-shot 1회 실행 (팔이 반응해 움직임 — 성공 여부 무관) — 30초 영상 + 로그
4. 추론 루프 latency 1회 측정 (4070, n=100) — OpenVLA 300ms 와 나란히 둘 비교 baseline 수치

**판정은 2026-09-21 한 번만 한다** (세부 판정표: 실기 전환 plan §5.4 — 4 미완은 통과 간주, 3 실패는 통과 간주 + v2.5 첫 항목을 디버깅으로). 기존 ROS2 드라이버 검증 순서 (모터 위치 명령 → 데이지체인 → 최소 URDF+RViz) 는 삭제가 아니라 **Stage 1 첫 주로 이동**했다. 결과 기록: `Studies/Hardware-Arm/spike/RESULT.md`.

## Stage 1 (2026.10-11, 2개월, 추가 지출 없음 — 스파이크로 디리스크된 본 빌드)

> 팔 키트·손목 카메라·작업대 자재가 2026.08 말-09 초에 선집행되므로 이 구간의 추가 지출은 없다.
> **선행**: 2026.09 스파이크 판정 통과 (2026-09-21, 실기 전환 plan §5.4). ROS2 드라이버 검증 (모터 위치 명령 → 데이지체인 → 최소 URDF+RViz) 은 본 절 첫 주에 수행한다.


### 목표
- pick-and-place 단순 동작 + 조립 완성 (케이블 정리·작업대 고정·손목 카메라 마운트)
- 안전 기초: 소프트 리밋 (관절 범위) + 토크 상한 + 물리 e-stop (전원 차단 스위치)
- ROS2 래핑: URDF + `feetech_ros2_driver` + ros2_control 노드 — **LeRobot 스택과 병행 운영** (데이터·학습 = LeRobot, 배포·통합 = ROS2). latency 를 (a) LeRobot 직결 / (b) ROS2 경유 두 경로로 측정해 (b)-(a) 를 **통합 오버헤드** 수치로 남긴다
- Isaac Sim 디지털 트윈 첫 사이클 (nice — Phase 6 이월 허용)
- **v2 선행 하드웨어**: 1분 영상 (teleop + 정책 실행 + e-stop) + URDF (2026.11 완주 목표)


### 이유
스파이크에서 LeRobot 경로 (teleop·녹화·정책 실행) 를 이미 검증했으므로 본 빌드는 완성도 + ROS2 층에 집중. **휴직 구간(-2027.02)이 연속 블록을 잡을 수 있는 마지막 기회**이고, 첫 하드웨어는 계획의 2-3배가 걸리므로 must 마감(2027.02 말) 앞에 버퍼를 두는 배치다 — 2026.12-2027.02 는 v2.5 마무리 + 지연 흡수 + 초기 패키징. 한 구간 1트랙 원칙에 따라 초기 패키징(2-3주)은 2027.02 단독 구간으로 분리하고, C++ 코어·DDS 서사화 트랙은 2027.02 말-03 에 배치한다 (career positioning spec §6.2 — `docs/superpowers/specs/2026-08-05-career-positioning-vla-edge-design.md`).


### 실행 머신

팔·카메라를 USB 로 물리는 기계와 무거운 연산을 돌리는 기계가 같아야 편하다. **Ubuntu PC (RTX 4070) 를 2026.09 자택으로 이전하는 것이 확정됐으므로 팔 옆 기계는 이 PC 다.** 원격 접속으로는 USB 장치를 붙일 수 없어 분리 구성을 검토했으나, 이전 확정으로 그 필요가 사라졌다.

**백업 경로는 보유 중인 Jetson Orin Nano 다** (맥북이 아니다). 4070 PC 를 쓸 수 없게 되는 경우에 대비한 대조이자, v3 실기 배포의 예행이다:

| 기계 | 판정 |
|---|---|
| **Jetson Orin Nano (8GB)** | **적합.** **256GB SSD + Ubuntu 22.04 설치 완료** 상태라 ROS 2 Humble 을 apt 로 깔고 Phase 3 절차를 그대로 재사용한다 (LeRobot 이 요구하는 Python 3.10 도 기본). SO-101 + LeRobot 구동 사례가 공개돼 있고 NVIDIA 공식 SO-101 코스의 기준 구성이기도 하다. 네이티브 리눅스라 `feetech_ros2_driver` 빌드에 문제가 없다. 저장 용량도 에피소드 영상에 충분하다. 한계 — Isaac Sim 불가, ACT 학습은 소규모 데이터셋 사례가 있으나 정석은 4070/RunPod |
| MacBook Pro 14 (M4 Pro) | **ROS2 작업 불가.** LeRobot 자체는 macOS Apple Silicon 공식 지원이라 teleop·record 는 되지만, ROS 2 는 macOS 바이너리 패키지가 없고 Docker Desktop for Mac 은 USB 패스스루를 지원하지 않아 팔을 컨테이너에 붙일 수 없다. LeRobot 전용 백업 경로로만 유효 |

부수 효과: Jetson 구성은 v3 (Jetson 실기 배포, README 부록 C) 의 예행이 된다 — 개발 기계와 배포 타깃이 같아진다.

**Jetson 경로에서 확인할 것** (공개 구동 사례에서 실제로 걸린 지점들):

| 항목 | 내용 |
|---|---|
| CUDA 스택 | Ubuntu 22.04 만 올린 상태면 CUDA·cuDNN 이 없어 PyTorch GPU 가 안 붙는다. `cat /etc/nv_tegra_release` / `dpkg -l nvidia-jetpack` 으로 JetPack·L4T 확인 |
| PyTorch 설치 | 스크립트 설치는 실패 보고. **NVIDIA 공식 deb** 사용, `cusparselt` 선행 설치, `numpy==1.26.0` 고정. conda(aarch64) + Python 3.10 |
| torchcodec | **aarch64 미지원** → LeRobot 이 pyav 로 자동 폴백 (ffmpeg 별도 설치 불요). 단 pyav 는 LeRobotDataset 선호 코덱 libsvtav1 을 같은 방식으로 다루지 못해, 필요 시 ffmpeg 를 libsvtav1 포함해 소스 빌드 |
| **카메라 2대 동시 30fps** | 공개 사례에서 실패해 한 대를 10fps 로 낮춤 (대역폭). 완화 시도 — MJPEG 강제 (YUYV 무압축이 주범), USB 허브 경유 금지·본체 직결, 서로 다른 USB 컨트롤러에 분산. **ACT 입력 품질에 직결되므로 팔 도착 전에 카메라만으로 먼저 확인한다** |
| 권한 | `/dev/ttyACM*` 접근 오류 → udev 규칙으로 정착. 캘리브레이션 실패 시 캐시 삭제 후 재시도 |

**Isaac Sim 사양 리스크** — Isaac Sim 5.1 최소 사양은 RTX 4080 / VRAM 16GB / RAM 32GB 인데 본 PC 는 12GB / 31GB 로 VRAM 이 미달이고 RAM 이 턱걸이다. 다만 공식 문서가 지원 불가로 규정한 것은 RT 코어가 없는 GPU (A100·H100) 이고, 16GB 미만은 "프레임당 16MP 초과 복잡 씬에서 어려움" 서술이다. 용도별 전망:

| 용도 | 전망 |
|---|---|
| Stage 1 — URDF 임포트 + Sim Joint State 매칭 (단일 팔) | 가장 가벼운 축이라 로컬 실행 가능 전망 |
| Phase 6 — 디지털 트윈 (팔 + 작업대 + 카메라) | 경계. 센서 수·렌더 해상도에 따라 갈림 |
| Isaac Lab RL (병렬 환경 다수) | 로컬 불가에 가까움 — Phase 6 진입 전 준비에서 이미 RunPod 로 배치됨 |

**하드웨어 증설은 선택지가 아니고** (RAM·GPU 변경 불가), **RunPod 이관도 GUI 작업에는 대안이 되지 못한다**:

- Isaac Sim 의 WebRTC 라이브스트리밍은 **UDP 47998** (미디어) + TCP 49100 (시그널링) 을 쓰고, 두 포트는 클라이언트에 하드코딩돼 있어 5.x 에서 변경할 수 없다. TCP 전용 스트리밍은 지원하지 않는다. 컨테이너 구동 시 `--network=host` 도 요구된다
- **RunPod 은 UDP 를 지원하지 않는다** (공식 문서: "Pods do not support UDP connections"). 노출 수단은 HTTP 프록시와 public IP + 직접 TCP 뿐이고, 관리형 컨테이너라 `--network=host` 지정도 불가하다
- **Tailscale 로 우회할 수도 없다.** 커널 모드는 `/dev/net/tun` 이 필요한데 RunPod 이 이를 노출하지 않아 `mknod: /dev/net/tun: Operation not permitted` 로 실패한다 (runc v1.2 부터 기본 device cgroup 에서 제외됨. RunPod 측 요청 이슈 `runpod/runpodctl#272` 는 Open 상태이며, 그 이슈가 막힌 용례로 "저지연 WebRTC 스트리밍" 을 그대로 적고 있다). 유저스페이스 모드 (`--tun=userspace-networking`) 는 실행되지만 gVisor netstack 이 TCP/UDP 를 종료하고 127.0.0.1 로 재전송해 **WebRTC ICE 의 source IP 검증이 실패**한다

| 워크로드 | RunPod |
|---|---|
| Isaac Lab RL 학습, Python API 로 씬 구성·USD 저장 (headless) | 가능 — 스트리밍 불필요 |
| **URDF 임포트·Joint State 시각 확인, 씬 편집 (GUI)** | **불가** |

**따라서 Isaac Sim GUI 를 돌릴 수 있는 곳은 본인 4070 PC 뿐이다.** PC 가 자택에 있으므로 (2026.09 이전 확정) GUI 는 로컬에서 직접 띄운다.

**Tailscale 경유 원격 GUI 는 출장지 등에서 원격으로 쓸 때의 선택지로 남는다** — 4070 PC 는 일반 리눅스 머신이라 커널 모드 Tailscale 이 정상 동작하고, tailnet 안에서는 UDP 47998 이 통하므로 Isaac Sim WebRTC 스트리밍을 그대로 쓸 수 있다 (`--/app/livestream/publicEndpointAddress` 를 tailscale IP 로 지정). RunPod 이 막힌 것은 제공자의 네트워크 정책 때문이지 Isaac Sim 이 원격을 못 해서가 아니다. 이 경로의 변수는 가정 회선 업로드 대역폭과 왕복 지연이며, 로컬 실행이 기본 경로이므로 필요해질 때 검증한다 (실행 보드 #12).

**Stage 1 의 Isaac Sim 항목을 위협하는 것은 접근성이 아니라 위 사양 미달이다.** 로컬에서 감당하지 못하는 것으로 드러나면 그 항목만 Phase 6 (2027.05-) 로 이월한다 — 나머지 6개 체크 항목은 Isaac Sim 없이 수행 가능하다.

로컬 사양이 GUI 워크로드를 감당하지 못하는 것으로 드러나는 경우의 대안은 RunPod 이 아니라 UDP 를 열 수 있는 제공자 (Vast.ai, GCP Omniverse Developer Workstation) 이며, 세팅 비용이 크므로 실제로 막히기 전에는 검토하지 않는다.

## 안전 메커니즘 설계 노트


> VLA / 양산 시스템의 "안전 메커니즘 부족" 의 직접 해결 증거. 면접에서 가장 강한 질문 영역.


- **위치 한계**: Joint 별 min/max position 검증. 위반 시 즉시 정지.
- **속도 한계**: rad/s 단위 한계. 위반 시 감속.
- **토크 한계**: STS3215 의 *present current* / *present load* 활용. 충돌 감지.
- **e-stop**: 별도 토픽 (`/emergency_stop`) — true 시 모든 모터 즉시 토크 OFF.
- **인터록 노드는 C++** — Python GIL latency 회피.
- **dual-channel**: 정상 명령 채널과 안전 채널 분리. 안전 채널이 우선.

## 왜 자작 팔인가


*"Brain ↔ Body 통합 SW 엔지니어"* 의 가장 완전한 증거. 본인 약점 (VLA 신입급) 을 본인 강점 (AMR ROS 실무 5년, 2021.06~ + 펌웨어 2.5년 하드웨어 이해) 으로 직접 깨는 카드.


### 실행 품질로 증명하는 3가지

latency 측정, e-stop, BOM 이해는 로보틱스 랩에서도 일상적으로 다룬다 — 항목 자체가 희소한 것이 아니다. 차별점은 양산 ROS 5년 경험자가 이것들을 제품 수준 감각 (측정 방법론, 안전 설계 관행, 원가 구조) 으로 수행한다는 **실행 품질**이다.

- **latency**: 추론 → 모터 명령까지 ms 단위 측정
- **안전 메커니즘**: e-stop, 토크 한계, 충돌 감지 직접 구현
- **양산 비용 이해**: DIY 팔 BOM 표 — "이 가격대에 이 성능까지"


### 보너스
- **LeRobot / Hugging Face 생태계 표준 하드웨어**를 쓰므로, teleop 데이터 수집 → LeRobot 포맷 데이터셋 → ACT 학습 → HF Hub 공개 (v2.5) 경로가 그대로 이어진다. 채용 관점에서 읽히는 것은 모터 브랜드가 아니라 이 파이프라인 경험이다.
- 펌웨어 직무로 지원하지 않지만 *이해의 폭* 으로 차별화.

### 카메라 구성

팔 키트에 카메라가 없으므로 별도로 갖춘다. LeRobot 표준은 **손목 1대 + 외부 1대**다.

| 위치 | 장비 | 사양 |
|---|---|---|
| 손목 (**팔로워** 그리퍼) | 추가 구매 (1-3만원) | 소형 UVC USB 웹캠, 640x480 @ 30fps |
| 외부 (전면 또는 상단) | 보유 ELP Stereo 활용 (RGB 한쪽 스트림) | 720p-1080p @ 30fps |
| 리더 | **없음** | — |

**리더에 달지 않는 이유**: 정책을 자율 실행할 때 리더는 존재하지 않는다. 카메라를 리더에 달면 데이터 수집 때와 자율 실행 때의 관측 분포가 완전히 달라져 학습이 무의미해진다. 관측 시점은 배포 시에도 존재하는 팔로워여야 한다. 부수적으로 리더는 사람이 계속 손으로 움직이는 팔이라 카메라 무게·케이블이 곧 조작 부하가 된다.

실전 주의 3가지:

- **동일 모델 2대를 쓰지 말 것** — USB 경로가 무작위로 바뀌어 5-10분마다 끊긴다. udev 규칙으로 물리 경로를 고정하거나 서로 다른 모델을 쓴다. ELP + 다른 웹캠 조합이면 자동으로 회피된다
- **배치는 전면-상단이 전면-측면보다 낫다** — 측면은 파지 중 그리퍼 팁에 가려진다. 공개 사례에서 이 조정을 포함해 성공률이 60% → 90% 로 올랐다
- **카메라를 물리적으로 고정하고 노출·화이트밸런스를 잠글 것** — 소량 (50 에피소드 급) 데이터로 학습한 모델은 시점 변화를 견디지 못한다

카메라가 실제로 필요해지는 시점은 teleop 데이터 수집, 즉 Stage 1 (2027.01-02) 이다. 팔보다 늦게 구매해도 된다.


**비채택 기록**:
- **Koch v1.1** (Dynamixel 기반, ROBOTIS 국내 부품 41.3만원 + 서드파티·3D 프린팅 = 총 49-60만원): 2026-07 검토 후 비채택. 1순위 타깃사 (Dynamixel 제조사) 액추에이터 정합이라는 이점이 있었으나, 채용 관점에서 결정적인 것은 "어느 회사 모터를 썼는가" 가 아니라 "LeRobot/HF 파이프라인으로 무엇을 했는가" 라고 판단했다. 실무 요인도 SO-101 우위 — 리더 모터 XL330-M077-T 준비기간 40일 (휴일 미포함) 배송지연 vs SO-101 3일, 3D 프린팅 부품 자체 조달 필요 (외주 시 약 11만원) vs 키트 포함. LeRobot 생태계에서도 Koch 는 지원 목록에 남아 있을 뿐 현행 표준은 SO-101 이다 (SO-100 은 공식 문서상 deprecated)
- 커스텀 XL330+XM430 풀세트 (BOM 약 150-225만원): 비용 약 3-4배 + 리더-팔로워 teleop 미지원 (별도 입력 장치 필요) → 비채택
- AR4 (스테퍼 기반, 약 50-100만): 토크 피드백 없음 → "안전 메커니즘" 증거 약화 → 비채택
- "SO-101 프레임에 Dynamixel 을 얹는" 절충: 불가. 프레임 STL 이 STS3215 치수·토크 전제라 브래킷·링크 전면 재설계가 되고, 그 순간 SO-101 을 고를 이유였던 생태계 정합도 함께 소멸한다 (LeRobot 의 SO-101 설정은 Feetech 버스 전제)

## 스파이크 (2026.10, 2-3주, 산출물 아님 = 리스크 검증)

> **미확정 (2026-07)**: 실행 시기 (9월 절충안 vs 원안 10월) 는 **8월 초 체크포인트**(`Studies/Phase 4/notes.md` 진행 보드) 확정 사항이다. Stage 2 구성 (6DOF 확장) 의 재설계는 2026.11 분기 재평가 안건으로 유지한다.


첫 하드웨어는 계획의 2-3배 걸린다. 본 빌드 (Stage 1) 전에 짧게 굴려 파이프라인을 먼저 검증한다.


- **범위**: 키트를 전부 조립하기 전에, 모터 1-2개만 버스에 물려 전기·소프트웨어 경로만 확인. 안 예뻐도 됨.
- **목표**: "**Feetech 버스 + `feetech_ros2_driver` + ros2_control** 이 내 환경에서 도는가" 만 확인. pick-and-place 아님.
- **출력**: 터지면 Stage 1 의 ROS2 통합 경로와 일정을 **2026 년 안에** 재산정. 분기 재평가 #1 (2026.11) 입력.


**완제품 키트라 스파이크의 형태가 바뀐다.** 부품 단위 조달이었다면 "2-DOF 분만 먼저 사서 검증" 이 가능했지만, 키트는 통짜 구매다. 따라서 스파이크는 **선구매가 아니라 선검증**으로 재정의한다 — 키트 도착 후 조립에 착수하기 전에 모터 몇 개만 물려 드라이버부터 확인한다. 리스크 검증이라는 목적은 그대로다.

검증 순서:

1. 모터 1개를 버스에 연결하고 `feetech_ros2_driver` (ros2_control 하드웨어 인터페이스) 로 위치 명령 1회 전달
2. 2개로 늘려 ID 충돌·데이지체인 동작 확인
3. 최소 URDF 1개 작성 → RViz 에서 joint state 반영 확인

3번까지 통과하면 조립을 시작한다. 1번에서 막히면 Stage 1 의 ROS2 드라이버 계획 자체를 재검토해야 하므로, 조립에 시간을 쓰기 전에 확인하는 것이 요점이다.

## Stage 1 (2027.01-02, 2개월, 약 1-3만원 — 스파이크로 디리스크된 본 빌드)

> 팔 키트 (약 55만원) 는 2026.09-10 에 선집행되므로, 이 구간의 추가 지출은 손목 카메라뿐이다.


### 목표
- pick-and-place 단순 동작
- URDF + ROS2 드라이버 (`feetech_ros2_driver` — ros2_control 하드웨어 인터페이스)
- Isaac Sim 디지털 트윈 첫 사이클
- **v2 선행 하드웨어**: 동작 영상 + URDF + Sim 임포트 영상 (1분, 2027.02까지)


### 이유
스파이크에서 드라이버 경로를 이미 검증했으므로 본 빌드는 조립과 동작 완성도에 집중. Phase 4 (VLA) 종료 후 단독 진행 — 한 구간 1트랙 원칙.


### 실행 머신

팔·카메라를 USB 로 물리는 기계와 무거운 연산을 돌리는 기계가 같아야 편하다. 전제는 **Ubuntu PC (RTX 4070) 의 자택 이전**이다 (조율 중, 2026-07-28). 원격 접속으로는 USB 장치를 붙일 수 없으므로, 이전이 무산되면 팔 옆에 둘 기계 (보유 노트북) 를 따로 세우고 학습·Sim 만 원격으로 보내는 분리 구성이 된다.

**Isaac Sim 사양 리스크** — Isaac Sim 5.1 최소 사양은 RTX 4080 / VRAM 16GB / RAM 32GB 인데 본 PC 는 12GB / 31GB 로 VRAM 이 미달이고 RAM 이 턱걸이다. 다만 공식 문서가 지원 불가로 규정한 것은 RT 코어가 없는 GPU (A100·H100) 이고, 16GB 미만은 "프레임당 16MP 초과 복잡 씬에서 어려움" 서술이다. 용도별 전망:

| 용도 | 전망 |
|---|---|
| Stage 1 — URDF 임포트 + Sim Joint State 매칭 (단일 팔) | 가장 가벼운 축이라 로컬 실행 가능 전망 |
| Phase 6 — 디지털 트윈 (팔 + 작업대 + 카메라) | 경계. 센서 수·렌더 해상도에 따라 갈림 |
| Isaac Lab RL (병렬 환경 다수) | 로컬 불가에 가까움 — Phase 6 진입 전 준비에서 이미 RunPod 로 배치됨 |

**하드웨어 증설은 선택지가 아니다** (RAM·GPU 변경 불가). 그런데 **RunPod 이관도 GUI 작업에는 대안이 되지 못한다** (2026-07-28 확인):

- Isaac Sim 의 WebRTC 라이브스트리밍은 **UDP 47998** (미디어) + TCP 49100 (시그널링) 을 쓰고, 두 포트는 클라이언트에 하드코딩돼 있어 5.x 에서 변경할 수 없다. TCP 전용 스트리밍은 지원하지 않는다. 컨테이너 구동 시 `--network=host` 도 요구된다
- **RunPod 은 UDP 를 지원하지 않는다** (공식 문서: "Pods do not support UDP connections"). 노출 수단은 HTTP 프록시와 public IP + 직접 TCP 뿐이고, 관리형 컨테이너라 `--network=host` 지정도 불가하다

| 워크로드 | RunPod |
|---|---|
| Isaac Lab RL 학습, Python API 로 씬 구성·USD 저장 (headless) | 가능 — 스트리밍 불필요 |
| **URDF 임포트·Joint State 시각 확인, 씬 편집 (GUI)** | **불가** |

**따라서 Stage 1 의 Isaac Sim 항목은 로컬 전용이고, PC 자택 이전이 편의가 아니라 선행 조건이 된다.** 원격 4070 에 X11/VNC 로 붙는 구성은 GPU 렌더를 원격 데스크톱으로 넘기는 것이라 성능·안정성 모두 권장되지 않는다. 로컬 사양이 GUI 워크로드를 감당하지 못하는 것으로 드러나면 대안은 RunPod 이 아니라 UDP 를 열 수 있는 제공자 (Vast.ai, GCP Omniverse Developer Workstation) 이며, 세팅 비용이 크므로 실제로 막히기 전에는 검토하지 않는다.

## 안전 메커니즘 설계 노트


> VLA / 양산 시스템의 "안전 메커니즘 부족" 의 직접 해결 증거. 면접에서 가장 강한 질문 영역.


- **위치 한계**: Joint 별 min/max position 검증. 위반 시 즉시 정지.
- **속도 한계**: rad/s 단위 한계. 위반 시 감속.
- **토크 한계**: STS3215 의 *present current* / *present load* 활용. 충돌 감지.
- **e-stop**: 별도 토픽 (`/emergency_stop`) — true 시 모든 모터 즉시 토크 OFF.
- **인터록 노드는 C++** — Python GIL latency 회피.
- **dual-channel**: 정상 명령 채널과 안전 채널 분리. 안전 채널이 우선.

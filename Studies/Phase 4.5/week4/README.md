| 조용히 틀릴 수 있는 것 | 증상 |

## 미리 풀어 두는 용어


| 용어 | 뜻 |
|---|---|
| **회수**(retrieval) | 클라우드에 남은 산출물을 로컬로 가져오는 것 |
| **무결성**(integrity) | 전송된 파일이 원본과 같다는 것. 파일 수·바이트 수·체크섬으로 확인한다 |
| **체크섬**(checksum) | 파일 내용을 요약한 짧은 값. 값이 같으면 내용이 같다고 본다 |
| **safetensors** | 모델 가중치를 저장하는 파일 형식. 7B 모델이면 여러 조각으로 나뉘어 있다 |
| **양자화**(quantization) | 가중치를 더 적은 비트로 표현해 메모리를 줄이는 것 |
| **4-bit / nf4** | 가중치 하나를 4비트로 저장하는 방식. `nf4` 는 그중 한 종류 |
| **double quant** | 양자화에 쓰는 보조 상수까지 한 번 더 양자화해 메모리를 더 줄이는 옵션 |
| **compute dtype** | 실제 계산에 쓰는 자료형. 저장은 4-bit 여도 연산은 fp16 으로 한다 |
| **`trust_remote_code`** | 표준 라이브러리에 없는 모델 코드를 체크포인트 쪽에서 받아 실행하도록 허용하는 옵션 |
| **processor** | 이미지·텍스트를 모델 입력 형식으로 바꿔 주는 전처리기 |
| **`unnorm_key`** | 모델 출력을 어느 데이터셋 통계로 역정규화할지 고르는 스위치 |
| **`norm_stats`** | 모델이 들고 있는 "데이터셋 이름 -> action 통계" 딕셔너리 |
| **값 대역**(range) | 값들이 놓이는 대략적 범위. 자릿수가 어긋나면 스케일 오류의 신호다 |
| **결정성**(determinism) | 같은 입력에 항상 같은 출력이 나오는 성질 |
| **greedy 디코딩** | 확률이 가장 높은 토큰만 고르는 방식. `do_sample=False` 가 이것이다 |
| **smoke test** | 세부 성능은 보지 않고 "전체가 일단 도는지" 만 보는 최소 확인 |
| **버전 매트릭스** | 라이브러리 이름과 버전을 표로 고정해 둔 것. 조합이 어긋나면 모델이 안 열린다 |
| **변인 통제** | 비교하려는 것 하나만 바꾸고 나머지는 전부 고정하는 것 |

## 핵심 개념


### 1. 전송의 실패는 조용하다


머지된 7B 가중치는 15GB 급이다. 이 규모의 전송에서 흔한 실패는 "중간에 끊겼는데 파일이 남아 있어 성공한 것처럼 보이는" 경우다. 파일이 존재하고 이름도 맞으므로 `ls` 로는 구분되지 않는다.


| 대응 | 이유 |
|---|---|
| 재개 가능한 전송 수단 | 끊긴 지점부터 이어받는다 |
| 파일 수 + 총 바이트 비교 | 누락을 잡는다 |
| 가능하면 체크섬 | 부분 손상을 잡는다 |


세 대응이 잡는 것이 다르다. 파일 수는 "몇 개가 아예 안 왔는지" 를, 총 바이트는 "내용이 잘렸는지" 를, 체크섬은 "바이트 수는 같은데 내용이 다른지" 를 잡는다. 위에서 아래로 갈수록 강하고 느리다.


특히 **통계 파일은 작아서 눈에 안 띈다.** 가중치만 확인하고 넘어가면 실습 3 에서 막힌다. 그때는 pod 를 이미 지웠을 수도 있다 — 그러면 학습을 다시 돌려야 한다.


### 2. 4-bit 양자화는 Phase 4 week6 과 같은 절차다


새로 배우는 것이 없다. `BitsAndBytesConfig` 로 nf4 를 지정해 로드하는 방식은 [Phase 4 week6](../../Phase%204/week6/README.md) 과 동일하고, 달라지는 것은 **모델 경로**뿐이다 — HuggingFace 허브 이름 대신 로컬 체크포인트 디렉터리를 준다.


양자화를 왜 하는지 한 줄로 복기하면: 7B 모델을 fp16 으로 올리면 약 15GB 라 12GB GPU 에 안 들어간다. 가중치를 4비트로 저장하면 약 1/4 로 줄어 들어간다. 계산은 fp16 으로 하되 저장만 4비트로 하는 방식이다.


로컬 경로 로드에서 확인할 것이 하나 있다. OpenVLA 는 표준 transformers 에 없는 자체 모델 코드를 함께 받아 실행한다 (`trust_remote_code`). 허브에서 받을 때는 그 코드가 허브에 함께 있어 자동으로 따라오지만, **로컬 디렉터리에서 로드할 때는 그 연결이 체크포인트 안에 보존돼 있어야 한다.** 없으면 로드 자체가 실패한다.


### 3. VRAM 은 baseline 과 대조해서 읽는다


week0 의 zero-shot 측정에서 이미 실측치가 있다. 4-bit OpenVLA 7B 의 적재 후 메모리는 약 4.4GB 였다 ([Measurements](../../../Measurements/openvla-rtx4070-int4/) 의 Block 1 결과).


fine-tuned 모델은 **구조가 같고 가중치 값만 다르다.** LoRA 는 층을 추가하지 않고, 머지는 값만 바꾼다. 따라서 적재 메모리도 거의 같아야 한다.


| 관측 | 해석 |
|---|---|
| baseline 과 근사 일치 | 정상 |
| 크게 크다 | 양자화가 적용되지 않았을 가능성 (설정 누락) |
| 크게 작다 | 모델이 일부만 로드됐을 가능성 |


즉 이 수치는 "12GB 에 들어가는가" 만 보는 값이 아니라 **양자화가 실제로 걸렸는지 판정하는 지표**다. 양자화 설정을 빠뜨리면 15GB 를 요구하다 OOM 으로 죽거나, GPU 와 CPU 에 나눠 올라가 느리게 도는 상태가 된다. 후자는 오류가 없어서 더 위험하다.


### 4. `unnorm_key` 를 자기 통계로 바꾸는 것이 이번 주의 기술 과제


week0 에서는 남의 로봇 통계(`bridge_orig`)를 빌려 썼다. 이유는 단순했다 — 내 통계가 없었기 때문이다. 이제 학습에 쓰인 내 데이터셋 통계로 바꿔야 한다.


```mermaid
flowchart LR
    A["week2 RLDS<br/>원시 단위 라벨"] --> B["week3 학습<br/>통계로 정규화"]
    B --> C["통계 파일<br/>실행 디렉터리에 저장"]
    C --> D["week4: 모델이 그 통계를<br/>읽을 수 있게 연결"]
    D --> E["predict_action<br/>unnorm_key = 내 데이터셋"]
```


왜 반드시 바꿔야 하는가. 학습이 정규화에 쓴 기준과 추론이 역정규화에 쓰는 기준이 같아야 값이 원래 물리량으로 돌아온다. 다른 기준을 쓰면 "cm 로 학습한 것을 inch 로 읽는" 것과 같은 일이 벌어진다.


이 연결이 안 되면 두 가지 중 하나가 일어난다 — 키를 찾지 못해 오류가 나거나, 옛 키(`bridge_orig`)로 역정규화되어 **스케일이 남의 로봇 기준으로 나온다.** 후자가 위험하다. 오류 없이 동작하고 값도 그럴싸하지만 전부 틀린다. 그리고 그 상태로 week5 측정을 돌리면 "fine-tuning 이 효과가 없었다" 는 결론이 나오는데, 실제 원인은 키 하나다.


판정 방법은 §7 에 있다.


### 5. 양자화는 변인이다 — zero-shot 도 같은 조건이어야 한다


4-bit 양자화는 가중치를 근사해 저장하는 것이므로 action 정확도를 떨어뜨릴 수 있다. 그러면 week5 의 before/after 비교에서 문제가 생긴다.


| 조건 | before (zero-shot) | after (fine-tuned) | 비교 가능? |
|---|---|---|---|
| 양쪽 모두 4-bit | 4-bit | 4-bit | 가능 — 변인은 모델 하나 |
| before 는 fp16, after 는 4-bit | fp16 | 4-bit | **불가** — 양자화와 adaptation 이 섞인다 |


두 번째 줄에서 성공률이 올랐다면 그것이 fine-tuning 덕분인지, 아니면 before 쪽이 양자화 손실로 불리했던 것인지 구분할 수 없다. 반대로 성공률이 떨어졌다면 adaptation 이 실패한 것인지 after 쪽만 양자화 손실을 입은 것인지 알 수 없다. **어느 방향이 나와도 해석이 막힌다.**


week0 baseline 을 4-bit 로 측정해 둔 것이 여기서 값을 한다. 이번 주에 할 일은 **그 조건이 실제로 같은지 확인**하는 것이다 — 같은 nf4 설정, 같은 double quant 여부, 같은 compute dtype. 세 항목 중 하나만 달라도 정밀도 조건이 달라진다.


### 6. 버전 매칭 — 학습 환경과 추론 환경은 다른 환경이다


학습은 컨테이너(week3), 추론은 로컬 `.venv-vla` 에서 돈다. 두 환경의 라이브러리 조합이 다르면 체크포인트가 로드되지 않거나, 로드돼도 다르게 동작한다.


정본은 [Phase 4 SETUP.md](../../Phase%204/SETUP.md) §7 의 버전 매트릭스다. 로컬 조합은 OpenVLA remote code 가 요구하는 범위로 이미 고정돼 있다 — 그 조합 위에서 Block 1-3 실측이 재현되므로 **로컬을 학습 환경에 맞추는 방향이 아니라, 체크포인트가 로컬 조합에서 열리는지 확인하는 방향**이다.


방향을 이렇게 정한 이유: 로컬 조합을 바꾸면 week0 baseline 을 측정한 환경이 달라진다. 그러면 before/after 의 before 쪽을 다시 재야 한다. 이미 확정된 것을 지키고 새로 들어오는 것을 검증하는 편이 싸다.


열리지 않으면 선택지는 두 개다.


| 선택 | 대가 |
|---|---|
| 로컬 조합을 조정 | Block 1-3 실측 재현성이 깨질 수 있다. 그러면 baseline 을 다시 재야 한다 |
| 학습 측 저장 형식을 조정해 재학습 | RunPod 사이클 하나를 다시 쓴다 |


어느 쪽도 싸지 않으므로 **이번 주에 검증하는 것 자체가 목적**이다. week5 에 가서 발견하면 eval 일정이 밀린다.


### 7. "로드된다" 는 통과가 아니다


이번 주의 통과 기준을 네 층으로 둔다. 위에서 아래로 갈수록 강하다. 각 층이 **다른 실패 원인을 배제**하도록 설계돼 있다.


| 층 | 검사 | 무엇을 배제하는가 |
|---|---|---|
| 1 | OOM 없이 적재된다 | 용량 문제 |
| 2 | 적재 메모리가 baseline 과 근사 일치 | 양자화 미적용 (§3) |
| 3 | `predict_action` 이 7차원을 반환하고 **값 대역이 학습 데이터 통계 대역과 맞는다** | `unnorm_key` 오연결 (§4) |
| 4 | 같은 입력에 같은 출력 (결정성) | 비결정 설정 잔존 |


3층이 핵심이다. 학습 데이터의 action 분포는 week1 실습 6 에서 히스토그램으로 봐 뒀고, 통계 파일에도 분위수가 있다. **모델 출력이 그 대역 안에 있는가**를 보면 역정규화가 제대로 걸렸는지 판정된다. 남의 통계로 역정규화되면 대역이 어긋난다 — 예를 들어 내 데이터의 위치 델타가 ±0.02 대역인데 출력이 ±0.4 로 나오면 다른 기준으로 되돌린 것이다.


4층이 필요한 이유: 결정적이지 않으면 week5 의 두 측정이 "같은 조건" 이라는 주장이 약해진다. 같은 seed 로 같은 모델을 돌렸는데 결과가 매번 다르면, before/after 차이가 모델 차이인지 실행 간 흔들림인지 구분할 수 없다.


### 8. 이번 주와 week5 의 경계


이번 주는 **1 episode** 를 돌려 모델이 루프에 꽂히는 것만 본다. 성공/실패는 판정하지 않는다.


| 주차 | 하는 일 | 하지 않는 일 |
|---|---|---|
| week4 | 모델이 하네스에서 도는지 확인 (smoke test) | 성공률 판단 |
| week5 | 동일 조건 N회 측정 | 모델 수정 |


경계를 지키는 이유: smoke test 에서 성공률을 보기 시작하면 표본 1-2 개로 결론을 내리게 되고, 그 인상이 week5 의 해석을 오염시킨다. 1 episode 가 성공하면 "되는구나" 라는 기대가 생기고, 실패하면 "역시 안 되나" 라는 실망이 생긴다. **둘 다 N=100 의 결과를 읽는 눈을 흐린다.**

## 이번 주 실습 & 다음 주 준비


### 이번 주 실습 과제

1. 회수·전송 + 무결성 검증 — `outputs/transfer_check.md`
2. `practice_load_4bit.py` — 4-bit 적재 + VRAM 실측 (baseline 대조)
3. `practice_unnorm_switch.py` — 통계 연결 + 값 대역 검사
4. `practice_compat_check.py` — 버전 대조 + 결정성 확인
5. `practice_smoke_test.py` — week0 하네스에 모델만 교체해 1 episode


### 이번 주 산출 (must / nice)

- must: 4-bit fine-tuned 모델 로컬 적재 + VRAM 실측 + `unnorm_key` 전환 + 4층 검증 통과 로그
- nice: 양자화 전후 메모리·속도 비교 표 (fp16 로 한 번 올려볼 여유가 있을 때만 — 15GB 라 4070 에는 안 올라간다는 점에 유의)


### 다음 주 (week 5) 준비

- week5 는 **모델만 교체**해 zero-shot 과 fine-tuned 를 동일 조건 N회 비교한다. 이번 주 smoke test 코드가 그 하네스의 원형이다
- 고정해 넘길 것: week0 의 seed 목록 / step cap / 카메라 키 경로 / instruction 문구 / 4-bit 설정 / 부분 도달률 판정식
- 즉 week5 에서 바뀌는 것은 모델 경로와 `unnorm_key` 두 개뿐이어야 한다. 그 외가 바뀌면 before/after 가 성립하지 않는다

## 이번 주 핵심 요약


1. **머지는 끝났다** — 이번 주는 전송 + 양자화 + 검증이다.
2. **VRAM 은 baseline 대조로 읽는다** — 양자화가 걸렸는지 판정하는 지표다.
3. **`unnorm_key` 를 내 통계로 바꾼다** — 안 바꾸면 남의 로봇 스케일로 조용히 틀린다.
4. **양자화 조건을 zero-shot 과 맞춘다** — 안 맞추면 양자화와 adaptation 이 섞인다.
5. **버전 검증을 이번 주에 한다** — week5 에서 발견하면 일정이 밀린다.
6. **로드는 통과가 아니다** — 값 대역까지 봐야 한다. smoke test 는 1 episode 까지.

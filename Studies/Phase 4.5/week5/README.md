## 이 문서를 읽는 법


- 이 문서는 **개념**(왜 이렇게 측정하는가), [`PRACTICE.md`](PRACTICE.md) 는 **절차**(무엇을 실행하고 무엇을 확인하는가) 다.
- 이번 주는 처음으로 **통계 용어**가 나온다. 어려운 수식은 필요하지 않고, "이 숫자로 무엇을 주장할 수 있는가" 를 다루는 도구라고 보면 된다. 용어는 아래 표에서 한 줄씩 풀어 둔다.
- 통계 방법의 **선택은 본인이 한다** (실습 3). 이 문서는 왜 선택이 필요한지와 무엇이 안 되는지를 설명하고, 어느 방법을 쓰라고 지정하지 않는다.


## 이번 주를 한 문장으로


> 하나의 스크립트에 모델 경로만 인자로 바꿔 넣어 **zero-shot 과 fine-tuned 를 완전히 같은 조건으로 각각 N회** 돌리고, seed 별 결과를 한 줄씩 파일에 기록한다. 그리고 결과를 **보지 않은 상태에서** 어떤 통계 방법으로 판정할지 먼저 문서로 확정한다.


이 주차의 특이한 점은 **코드가 거의 새로 없다는 것**이다. sim 루프는 week0, 모델 적재는 week4 에서 이미 만들었다. 그런데도 한 주를 쓰는 이유는 두 가지다.


| 이유 | 설명 |
|---|---|
| 변인이 새면 앞의 5주가 무효가 된다 | 전처리 한 줄, 설정 한 항목이 두 측정에서 다르면 before/after 를 말할 수 없다 (§1) |
| 방법을 결과보다 먼저 정해야 한다 | 결과를 본 뒤에 방법을 고르면 방법이 결과에 맞춰진다 (§7) |

## 미리 풀어 두는 용어


| 용어 | 뜻 |
|---|---|
| **eval harness** | 평가를 자동으로 돌리는 장치 전체 — 환경 생성, 루프, 판정, 기록 코드의 묶음 |
| **변인**(variable) | 결과에 영향을 줄 수 있는 조건. 비교에서는 하나만 바꾸고 나머지를 고정한다 |
| **변인 통제** | 비교 대상 외의 조건을 전부 같게 유지하는 것 |
| **N** | 반복 측정 횟수. 여기서는 평가할 episode 개수 |
| **성공률** | 성공한 episode 수 / N |
| **표본**(sample) | 관측된 결과들의 모음. N 이 표본 크기다 |
| **신뢰구간**(confidence interval) | "참값이 이 범위 안에 있을 것" 이라고 말하는 구간. N 이 작으면 넓어진다 |
| **정규 근사** | 성공률의 불확실성을 정규분포로 어림하는 방법. 경계(0% / 100%) 에서 무너진다 |
| **이항 비율** | "성공/실패 두 값만 나오는 시행" 의 성공 비율. 우리 성공률이 이 형태다 |
| **짝지은 관측**(paired) | 같은 문제(seed) 에 대해 두 조건의 결과를 나란히 가진 형태 |
| **불일치 쌍**(discordant pair) | 두 조건의 결과가 갈린 seed. 한쪽만 성공한 경우 |
| **검정력**(power) | 실제로 차이가 있을 때 그것을 잡아낼 확률 |
| **유의 수준** | 판정의 엄격함을 정하는 기준값. 보통 0.05 를 쓴다 |
| **부분 도달률** | 최종 성공 외에 중간 단계 도달 여부까지 세분한 지표 (week0 §7) |
| **원시 결과**(raw result) | 집계 전 개별 관측 기록. seed 별 한 줄씩 |
| **jsonl** | 한 줄에 json 하나씩 적는 파일 형식. 실행 중에도 이어 붙이기 쉽다 |
| **latency** | 한 번의 추론에 걸리는 시간 |
| **결정적 추론** | 같은 입력에 항상 같은 출력. `do_sample=False` |
| **사후 정당화** | 결과를 보고 나서 그 결과에 유리한 기준을 고르는 것. 분석이 아니다 |

## 핵심 개념


### 1. 이 주차의 난이도는 코드가 아니라 통제다


할 일은 이미 있는 코드를 두 번 돌리는 것이다. 그런데 여기서 실패하면 앞의 다섯 주가 무효가 된다. 실패의 형태는 하나다 — **모르는 사이에 변인이 하나 더 바뀌는 것.**


왜 그것이 치명적인가. before/after 비교의 논리는 "조건을 전부 같게 두고 모델만 바꿨으니, 차이는 모델 때문이다" 다. 조건 하나가 함께 바뀌면 그 논리가 끊어지고, 차이를 무엇으로도 귀속시킬 수 없다.


흔한 경로:


| 새는 지점 | 어떻게 새는가 |
|---|---|
| 리사이즈·전처리 | zero-shot 을 week0 코드로, fine-tuned 를 week4 코드로 돌리면 미묘하게 다를 수 있다 |
| 4-bit 설정 | double quant 나 compute dtype 하나가 다르면 정밀도 조건이 달라진다 |
| seed 목록 | 재측정 시 범위를 다시 만들면 목록이 어긋난다 |
| step cap | "조금 늘려 볼까" 가 두 측정에 다르게 적용된다 |
| instruction | 문구를 다듬으면 프롬프트가 달라진다 |


다섯 개 모두 **"고치려는 선의" 에서 나온다**는 공통점이 있다. 두 번째 측정을 하면서 코드를 조금 개선하는 것이 자연스러운 충동인데, 그 개선이 비교를 깨뜨린다.


대책은 하나다. **두 측정이 같은 스크립트, 같은 상수, 같은 파일에서 나오게 한다.** 스크립트를 복사해 고치지 않는다 — 모델만 인자로 받는다. 복사본이 두 개 있으면 한쪽만 고치는 일이 반드시 일어난다.


### 2. N 을 올려야 한다


week0 의 N=20 은 "루프가 닫힌다" 를 보이는 baseline 이었다. eval harness 에서는 다르다 — 이제 숫자로 판단을 해야 하고, N=20 의 구간은 판단을 지탱하지 못한다.


N 이 작으면 왜 판단이 안 되는지 감각을 잡아 둔다. 20번 중 5번 성공(25%) 을 관측했을 때, 참 성공률이 10% 인 경우에도 20번 중 5번은 충분히 나올 수 있다. 40% 인 경우에도 나올 수 있다. 즉 **관측값 하나로 좁혀지는 범위가 너무 넓다.** N 을 늘리면 그 범위가 좁아진다.


비용을 실측치로 계산해 보면 올릴 여지가 크다.


| 항목 | 값 | 출처 |
|---|---|---|
| 추론 1회 | 약 300 ms | [Measurements](../../../Measurements/openvla-rtx4070-int4/) Block 1 |
| episode 당 스텝 | 최대 100 (성공 시 조기 종료) | week0 step cap |
| episode 당 최대 시간 | 약 30초 | 위 둘의 곱 |
| N=20 | 약 10분 / 모델 | |
| N=100 | 약 50분 / 모델 | |


즉 **N=100 을 두 모델에 돌려도 두 시간 남짓**이다. sim 이라 사람이 지킬 필요도 없다. 이것은 원래 계획과도 맞는다 — week0 노트가 "정밀 성공률은 v1.5 eval harness 에서 N 을 키워 재측정" 이라고 이관해 뒀다.


대가가 하나 있다. **N 을 바꾸면 zero-shot 도 다시 재야 한다.** before/after 는 같은 N, 같은 seed 목록이어야 하므로 week0 의 20회 결과를 그대로 쓸 수 없다. 재측정 비용이 50분이라 이 대가는 싸다 (실습 4). 그리고 재측정에는 덤이 있다 — week0 과 겹치는 seed 의 결과가 일치하는지 보면 **week0 재현 검사**가 된다.


### 3. 0/N 에 "±0" 을 붙이면 안 된다


성공률의 표준오차를 정규 근사로 계산하면 성공률이 0 이거나 1 일 때 **폭이 0 이 된다.** 계산식이 성공률과 실패율의 곱을 쓰기 때문에, 한쪽이 0 이면 곱도 0 이 되는 구조다.


그래서 0/20 을 관측했을 때 "0% ± 0%" 라는 값이 나오는데, 이것은 명백히 틀린 보고다 — 20회 관측으로 참 성공률이 정확히 0 이라고 말할 수는 없다. 참 성공률이 3% 인 정책도 20회 중 0회 성공이 흔하게 나온다.


| 상황 | 정규 근사 | 문제 |
|---|---|---|
| 10/20 | 폭이 넓게 나옴 | 대략 쓸 수 있다 |
| 0/20 | 폭 0 | **쓸 수 없다** |
| 1/20 | 폭이 비현실적으로 좁음 | 신뢰할 수 없다 |


우리 상황에서 before 쪽이 0/N 일 가능성이 높으므로 (week0 §7), 이 문제를 우회할 수 없다. 경계에서도 성립하는 구간 추정 방법을 써야 한다 — 근사를 보정하는 계열과 근사를 쓰지 않는 계열이 있다. **어느 방법을 쓸지와 그 이유를 실습 3 에서 정하고 기록한다.**


판정에 쓰는 문장의 형태가 이렇게 바뀐다.


- 나쁨: "zero-shot 0%, fine-tuned 25% 로 향상"
- 좋음: "zero-shot 0/100 (95% 구간 상한 약 X%), fine-tuned 25/100 (구간 Y-Z%). 두 구간이 겹치지 않는다"


두 번째 문장이 왜 더 나은가. 분자/분모가 있어 N 을 알 수 있고, 구간이 있어 불확실성의 크기를 알 수 있고, "겹치지 않는다" 는 판정의 근거가 문장 안에 있다. **읽는 사람이 검증할 수 있는 형태**다.


### 4. 같은 seed 를 쓴다는 사실은 통계적 자산이다


두 측정에 같은 seed 목록을 쓰므로, 결과는 **독립 두 집단이 아니라 짝지어진 관측**이다. 같은 초기 배치에 대해 두 모델의 성패를 나란히 갖고 있다.


비유하면 이렇다. 두 학생의 실력을 비교할 때 서로 다른 시험지를 주면 점수 차이에 문제 난이도가 섞인다. 같은 시험지를 주면 문항별로 누가 맞혔는지 비교할 수 있고, 문항 난이도는 양쪽에 똑같이 작용하므로 상쇄된다.


| 관점 | 독립 두 집단으로 볼 때 | 짝지어진 것으로 볼 때 |
|---|---|---|
| 쓰는 정보 | 성공 횟수 두 개 | seed 별 성패 조합 |
| task 난이도 편차 | 잡음으로 들어간다 | 같은 seed 끼리 비교되어 상쇄된다 |
| 검정력 | 낮다 | 높다 |


핵심은 **"둘 다 실패한 seed" 와 "둘 다 성공한 seed" 는 차이에 대한 정보가 없고, 한쪽만 성공한 seed 만 정보를 준다**는 점이다. 두 모델이 똑같이 실패한 문제는 어느 쪽이 나은지 알려주지 않는다. 반대로 fine-tuned 만 성공한 문제가 여러 개이고 zero-shot 만 성공한 문제가 거의 없다면, 그것이 개선의 근거다. 그 불일치 쌍의 개수와 방향이 판단의 근거가 된다.


따라서 결과를 **seed 별로** 저장해야 한다. 성공 횟수만 남기면 이 정보가 사라진다 (§6).


### 5. 부분 도달률도 같은 방식으로 본다


최종 성공률이 양쪽 모두 0 에 가까울 수 있다 (week0 §7). 그때 신호는 부분 도달률에서 나온다.


| 단계 | zero-shot | fine-tuned | 비교 |
|---|---|---|---|
| reached | | | 짝지은 비교 |
| grasped | | | 짝지은 비교 |
| lifted | | | 짝지은 비교 |
| placed (= 성공) | | | 짝지은 비교 |


단계별로 같은 절차를 적용한다. **어느 단계에서 차이가 생겼는지**가 week6 분석의 재료다 — "접근은 좋아졌지만 파악에서 막혔다" 같은 진술이 여기서 나온다. 이 진술은 성공률 하나만 봤을 때는 만들 수 없다.


판정식과 임계값은 week0 에서 정한 것을 그대로 쓴다. 여기서 조정하면 before 와 after 의 기준이 달라진다. 특히 "임계값을 조금 느슨하게 하면 신호가 보일 텐데" 라는 생각이 들 수 있는데, 그것을 결과를 본 뒤에 하면 §7 의 사후 정당화가 된다.


### 6. 원시 결과를 seed 단위로 즉시 저장한다


두 가지 이유다.


- **짝지은 비교에 필요하다** (§4). 집계값만 남기면 불가능해진다
- **중단에 대비한다.** N=100 이면 실행이 한 시간 단위다. 중간에 죽으면 그때까지의 결과가 남아야 한다


"즉시" 가 붙는 이유: 결과를 리스트에 모아 두고 마지막에 한 번 저장하면, 90번째에서 죽었을 때 89개가 함께 사라진다. 한 줄씩 파일에 쓰고 버퍼를 비우면 죽은 시점까지의 결과가 남는다. jsonl 형식을 쓰는 이유가 이것이다 — 한 줄이 하나의 완결된 기록이라 이어 붙이기 쉽다.


저장할 항목:


| 항목 | 용도 |
|---|---|
| seed | 짝지음의 키 |
| 4단계 도달 여부 | 단계별 비교 |
| 종료 스텝 수 | 효율 비교 (성공까지 몇 스텝) |
| 종료 사유 | 성공 / step cap / 환경 종료 구분 |
| 모델 식별자 | 경로 + `unnorm_key` |
| 실행 메타 | 실행 시각, 스크립트 버전(커밋), 4-bit 설정 |


마지막 줄이 중요하다. 나중에 "이 결과가 어느 조건에서 나왔나" 를 물을 때 답이 파일 안에 있어야 한다. 기억이나 별도 메모에 의존하면, 두 결과 파일의 조건이 같았는지를 **코드로 검사할 수 없다** (실습 5 의 메타 대조가 그 검사다).


### 7. 이번 주는 해석하지 않는다


결과를 보면 즉시 해석하고 싶어진다. 그러나 이번 주의 산출물은 **원시 결과와 방법의 확정**까지다.


| 주차 | 하는 일 |
|---|---|
| week5 | 하네스 통합, N 결정, 통계 방법 확정, 두 측정 실행, 원시 결과 저장 |
| week6 | 구간 계산, 짝지은 비교, 원인 분석, 블로그 |


이유는 week4 §8 과 같다. 집계값을 먼저 눈으로 보고 나면 그 인상에 맞는 해석을 찾게 된다. 더 구체적으로는, 결과가 아쉬울 때 "유의 수준을 0.1 로 하면" 이나 "단측 검정으로 하면" 같은 조정을 하고 싶어진다. 그 조정 자체가 통계적으로 틀린 것은 아니지만, **결과를 본 뒤에 고르면 그것은 분석이 아니라 사후 정당화**다.


방법을 **결과를 보기 전에** 정해 두는 것이 이 순서의 목적이다 (실습 3 이 실습 4-5 보다 앞에 있는 이유).

## 자체 점검


문서를 보지 않고 답한다. 막히면 해당 절로 돌아간다.


**Q1.** 두 측정 사이에 변인이 새는 경로를 3개 이상 들고, 공통 대책을 말하라. (§1)


**Q2.** N 을 올리기로 판단한 근거를 실측치로 계산해 보이라. 그 대가는 무엇인가. (§2)


**Q3.** 0/20 에 정규 근사 구간을 쓰면 안 되는 이유는. 그리고 우리 상황에서 이 문제를 왜 우회할 수 없는가. (§3)


**Q4.** 같은 seed 를 쓴 것이 통계적 이점이 되는 이유는. 어떤 seed 가 차이에 대한 정보를 주는가. (§4)


**Q5.** 최종 성공률이 양쪽 모두 0 일 때 무엇을 보는가. 그 기준을 이번 주에 조정하면 안 되는 이유는. (§5)


**Q6.** 집계 성공률만 저장하면 무엇이 불가능해지는가. (§6)


**Q7.** 통계 방법을 결과를 보기 전에 정하는 이유는. (§7)

## 이번 주 핵심 요약


1. **난이도는 통제다** — 두 측정이 같은 스크립트·같은 상수에서 나오게 한다.
2. **N 을 올린다** — 실측 300 ms 기준으로 N=100 이 두 시간 남짓이다. zero-shot 재측정 비용도 싸다.
3. **0/N 에 정규 근사를 쓰지 않는다** — 경계에서 성립하는 구간 추정을 쓴다.
4. **같은 seed 는 자산이다** — 짝지은 비교로 검정력을 얻는다. 그래서 seed 단위로 저장한다.
5. **부분 도달률도 단계별로 비교한다** — 기준은 week0 것을 그대로 쓴다.
6. **해석은 week6** — 방법을 결과보다 먼저 정한다.

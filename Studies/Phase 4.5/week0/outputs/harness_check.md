## 결론

**통과.** 정답 좌표를 아는 해법을 이 측정 장치에 넣었을 때 20/20 성공했다. 따라서 환경 설정, episode 루프, 성공 판정, step 예산, 정규화 action 경로는 정상이다. 실습 6 의 zero-shot 성공률이 0 으로 나와도 그것을 "장치 고장" 이 아니라 "정책의 성적" 으로 읽을 수 있다.

단 두 가지가 남는다.

- OpenVLA 출력을 ManiSkill action 으로 번역하는 **변환 레이어는 이 검증으로 배제되지 않는다** (아래 §배제 범위).
- 20 seed 중 **1개(seed08)는 아무것도 하지 않아도 성공한다** (아래 §하한 대조). 실습 6 의 성공률을 이 하한과 함께 읽어야 한다.

## 왜 이 검증을 먼저 하는가

실습 6 에서 성공률 0% 가 나오면 원인이 두 갈래다. (a) 모델이 이 sim 화면을 처음 봐서 못 하는 것, (b) 내가 만든 환경·루프·판정·변환이 고장난 것. 두 원인이 똑같은 숫자를 만들기 때문에, 숫자를 먼저 재면 그 숫자를 해석할 수 없다.

그래서 성공률과 무관하게 "장치는 정상이다"를 먼저 증명한다. 방법은 **정답을 아는 해법을 넣어 보는 것**이다. 정답을 아는 해법이 실패하면 그건 해법 탓이 아니라 장치 탓이다.

## 어떤 해법을 썼는가 — motion planning 이 아니라 scripted

ManiSkill 에는 PickCube 용 **motion planning** 해법(`examples/motionplanning/panda/solutions/pick_cube.py`)이 들어 있다. motion planning 은 물체 좌표를 직접 읽어 손이 갈 경로를 기하학적으로 계산하는 고전 방식이다. 이것을 쓰려 했으나 **이 환경에서는 실행 자체가 불가능했다.**

| 항목 | 사실 |
|---|---|
| 증상 | `mplib.Planner` 를 만드는 순간 파이썬 프로세스가 세그폴트로 죽는다 (`mplib/planner.py:65`) |
| 원인 | `mani_skill 3.0.1` 이 `mplib==0.1.1` 을 핀으로 요구하고, 그 바이너리는 numpy 1.x 의 C API 로 빌드돼 있다. 설치된 numpy 는 2.5.1 이라 ABI 가 맞지 않는다 |
| 증거 | `mplib/pymp*.so` 안에 `numpy.core` (numpy 2 에서는 `numpy._core` 로 이름이 바뀐 모듈) 와 `FAILURE obtaining numpy _ARRAY_API pointer` 문자열이 있다 |
| 우회 시도와 결과 | numpy 를 1.26.4 로 내리면 mplib 은 살지만 `scipy 1.18.0` 과 `opencv-python 5.0.0.93` 이 numpy>=2 를 요구해 그쪽이 깨진다 (`AttributeError: module 'numpy' has no attribute 'long'`). numpy 는 2.5.1 로 되돌렸다 |

`ABI`(Application Binary Interface)는 컴파일된 바이너리끼리 데이터를 주고받는 규약이다. C 확장 모듈은 빌드 시점의 numpy 헤더에 맞춰 컴파일되므로, 실행 시 numpy 의 메이저 버전이 다르면 포인터를 잘못 읽어 그대로 죽는다. 파이썬 예외가 아니라 세그폴트로 나오는 이유가 이것이다.

그래서 README §8 이 함께 허용하는 **scripted 해법**을 썼다. 큐브와 목표의 좌표를 시뮬레이터에서 직접 읽어(카메라를 보지 않는다) 아래 5단계로 손을 움직인다.

| 단계 | 하는 일 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| above | 큐브 위 5 cm 지점으로 이동, 그리퍼 열림 | 목표점까지 거리 < 0.008 m |
| descend | 큐브 중심 높이까지 하강 | 거리 < 0.006 m |
| close | 제자리에서 그리퍼 닫기 | 8 step 유지 |
| lift | 큐브를 든 채 목표 지점으로 이동 | 큐브-목표 거리 < 0.02 m |
| hold | 정지 | success 판정이 `is_robot_static` 을 요구하므로 필요 |

회전 델타는 전 단계에서 0 이다. Panda 의 초기 자세가 이미 그리퍼를 아래로 향하고 있어(초기 TCP 쿼터니언이 x 축 180도 회전에 가깝다) 위치 제어만으로 큐브를 집을 수 있다.

**바꿔 쓴 것이 손해가 아니다.** motion planning 은 관절 각도 명령(`pd_joint_pos`)을 쓰므로 실습 6 과 `control_mode` 가 달라진다. scripted 해법은 실습 6 과 같은 `pd_ee_delta_pose` 를 쓰므로, `[-1, 1]` 정규화 action 이 물리량으로 풀리는 경로까지 함께 검증된다. 즉 검증 범위가 더 넓다.

## 하한 대조 결과 — 공짜로 얻는 성공 1개

상한만 재고 넘어가면 놓치는 것이 있다. PickCube 는 목표 지점을 매 episode 무작위로 뽑기 때문에, **목표가 큐브 초기 위치 바로 옆에 떨어지는 배치**가 섞인다. 그런 episode 는 `is_obj_placed` 가 reset 직후부터 True 이고, 로봇이 가만히 있으면 `is_robot_static` 도 True 이므로 성공으로 집계된다.

실제로 발견됐다. 상한 대조에서 seed08 만 `steps=9`, `is_grasped=False` 로 성공했다 — 큐브를 잡지도 않고 성공한 것이다.

| 확인 항목 | 값 |
|---|---|
| seed08 의 초기 cube-goal 거리 | **0.0148 m** |
| `goal_thresh` (성공 판정 임계값) | 0.025 m |
| 20 seed 중 초기부터 `is_obj_placed=True` 인 것 | seed08 하나 |
| 무행동 정책(전 차원 0 인 action)의 성공률 | **1/20** (seed08) |

**실습 6 에 적용할 규칙**: seed08 에서 나온 성공은 조작 능력의 증거가 아니다. 성공률을 보고할 때 하한을 함께 적는다. 예를 들어 `placed 1/20` 이 나왔고 그것이 seed08 이면, 실질 성공은 0 이다. 이 값을 모르면 정책의 성과와 초기 배치 운을 구분할 수 없고, 같은 혼동이 fine-tuned 측정과의 before/after 비교에서 반복된다.

seed 목록은 `list(range(20))` 을 그대로 유지한다. seed08 을 빼면 PickCube 의 원래 초기 배치 분포보다 인위적으로 어려운 조건이 되어 공개 수치와의 비교 가능성이 떨어진다. 빼는 대신 **하한을 기록해 해석 단계에서 걷어낸다.**

## 이 검증이 배제한 용의자와 배제하지 못한 것

| 용의자 | 배제됐나 | 근거 |
|---|---|---|
| 환경 설정 (`obs_mode` / `control_mode` / 카메라) | 배제 | 같은 설정에서 20/20 성공 |
| episode 루프 (reset, step, 종료 조건) | 배제 | 같은 루프 구조로 성공이 집계됨 |
| 성공 판정 정의 | 배제 | 성공을 실제로 감지했다. 판정이 도달 불가능한 조건이 아니다 |
| step 예산 200 | 배제 | 최대 49 step 으로 충분 |
| `[-1, 1]` 정규화 action 이 물리량으로 풀리는 경로 | 배제 | scripted 해법이 이 경로로 팔을 정확히 움직였다 |
| **OpenVLA 출력을 번역하는 변환 레이어** | **배제 안 됨** | scripted 해법은 이 함수를 지나가지 않는다 |
| **시각 입력 경로** (모델이 받는 이미지가 실제로 장면을 담고 있는가) | **부분적** | 렌더 자체는 `outputs/env_check.png` 로 확인했으나, scripted 해법은 이미지를 쓰지 않으므로 관측 카메라 이미지가 정책에 제대로 전달되는지는 실습 6 에서 별도로 확인해야 한다 |

즉 실습 6 에서 0% 가 나오면 남은 가설은 **도메인 갭** 또는 **변환 레이어 버그** 두 개다. 이 둘을 더 가르려면 README §8 의 (b) 공개 수치 대조가 필요하다.

## 이 기록의 한계

- **scripted 해법은 공식 기성 해법이 아니다.** 이번 검증을 위해 직접 작성한 코드이고, 임계값(0.008 / 0.006 m, 8 step, 3 cm/step)도 직접 정한 값이다. 20/20 은 "좌표를 아는 정책이면 이 장치에서 성공이 집계된다"의 증거이지, ManiSkill 공식 성능 수치가 아니다.
- **(b) 공개 수치 대조는 하지 않았다.** 따라서 변환 레이어는 미검증으로 남는다.
- 무행동 하한은 seed 0-19 에 대해서만 확정된 값이다. seed 목록을 바꾸면 다시 재야 한다.

## 미리 풀어 두는 용어


| 용어 | 뜻 |
|---|---|
| **LoRA**(Low-Rank Adaptation) | 원래 가중치는 얼려 두고, 작은 보조 행렬만 학습해 모델을 적응시키는 방법 |
| **frozen**(얼린) | 학습 중 값을 갱신하지 않는 가중치. 그래디언트도 옵티마이저 상태도 필요 없다 |
| **base 가중치** | 사전학습된 원래 모델의 가중치. 여기서는 OpenVLA 7B |
| **7B** | 파라미터 70억 개. 가중치 1개가 2바이트면 약 15GB 가 된다 |
| **bf16 / fp16** | 숫자 하나를 2바이트로 저장하는 부동소수점 형식. fp32(4바이트) 의 절반 |
| **옵티마이저 상태** | 학습 중 갱신을 매끄럽게 하기 위해 파라미터별로 들고 있는 추가 값 (모멘텀 등) |
| **활성값**(activation) | 순전파 중 각 층이 내놓은 중간 결과. 역전파에 필요해서 메모리에 남는다 |
| **rank** | LoRA 보조 행렬의 크기를 정하는 값. 크면 표현력이 늘고 메모리·시간도 늘어난다 |
| **batch size** | 한 번의 순전파·역전파에 함께 넣는 샘플 수 |
| **grad accumulation** | 여러 스텝의 그래디언트를 모아 한 번만 갱신하는 기법. 유효 배치를 유지하며 메모리를 줄인다 |
| **유효 배치**(effective batch) | `batch size x grad accumulation`. 실제 갱신 1회가 몇 샘플을 반영하는지 |
| **OOM**(out of memory) | GPU 메모리 부족으로 실행이 죽는 것 |
| **step / max_steps** | 학습 갱신 1회 / 총 몇 회 갱신할지의 상한 |
| **probe** | 본 실행 전에 아주 짧게 돌려 시간·메모리를 재는 예비 실행 |
| **체크포인트** | 학습 중간 상태를 파일로 저장한 것. 중단 시 여기서 재개한다 |
| **network volume** | pod 를 지워도 남는 클라우드 저장 공간 |
| **Community Cloud** | 개인 제공 GPU 를 싸게 쓰는 등급. 대신 인스턴스가 회수될 수 있다 |
| **회수**(preemption) | 클라우드가 인스턴스를 강제로 되가져가는 것 |
| **Docker 이미지** | OS·라이브러리·코드를 한 덩어리로 굳힌 실행 환경 스냅샷 |
| **torchrun** | 분산 학습 실행기. GPU 1개여도 upstream 스크립트가 이것으로 실행되도록 쓰여 있다 |
| **tmux** | SSH 가 끊겨도 프로세스가 계속 돌게 해 주는 터미널 세션 관리자 |
| **머지**(merge) | LoRA 보조 행렬을 base 가중치에 합쳐 하나의 모델로 만드는 것 |

## 핵심 개념


### 1. 4070 으로 안 되는 이유는 옵티마이저가 아니다


흔한 오해부터 정정한다. LoRA 를 12GB 에서 못 돌리는 이유는 옵티마이저 상태나 활성값 때문이 아니다.


LoRA 의 발상을 먼저 한 줄로: 7B 개의 가중치를 전부 갱신하는 대신, 원래 가중치는 **얼려 두고**(frozen) 옆에 작은 보조 행렬을 붙여 그것만 학습한다. 학습 대상이 1/1000 이하로 줄어드니 학습이 가벼워진다 — 는 것이 흔한 설명이다. 그런데 그 "가벼워짐" 이 어느 항목에 적용되는지를 정확히 봐야 한다.


| 항목 | 크기 | 비고 |
|---|---|---|
| **frozen base 가중치 (bf16)** | **약 15GB** | 7B x 2바이트. **이것만으로 12GB 를 넘는다** |
| LoRA 어댑터 가중치 | 수십 MB | rank 32 기준 |
| 어댑터의 옵티마이저 상태 | 수백 MB | 학습 대상이 어댑터뿐이라 작다 |
| 활성값 | 배치에 비례 | batch 를 줄이면 줄어든다 |


즉 **바닥을 결정하는 것은 frozen base 다.** LoRA 의 이점은 "학습 대상을 줄여 옵티마이저·그래디언트를 줄이는 것" 이지 base 를 줄이는 것이 아니다. 얼려 둔 가중치도 순전파에 쓰이므로 GPU 에 올라가 있어야 한다. batch 를 1 로 줄여도 15GB 는 그대로 남는다.


upstream 이 제시하는 수치도 이 구조와 맞는다 — 배치 16 에서 약 72GB, 배치를 줄이면 **약 27GB 까지** 내려간다. 27GB 라는 하한이 존재하는 이유가 바로 base 가중치이고, 그래서 24GB 급 GPU 가 필요하다. (24GB 로 27GB 하한을 다루는 방법이 §2 다.)


### 2. batch size 와 grad accumulation


메모리를 줄이면서 학습의 성질을 유지하는 표준 수단이다.


- **batch size** 를 줄이면 활성값이 줄어 메모리가 내려간다. 대신 한 스텝의 그래디언트가 노이즈해진다 — 샘플 1개로 방향을 정하면 그 샘플의 특성에 휘둘린다
- **grad accumulation** 은 여러 스텝의 그래디언트를 모아 한 번 갱신한다. 유효 배치를 유지하면서 메모리를 낮춘다
- 대가는 시간이다. 유효 배치를 유지하려면 순전파·역전파 횟수가 그만큼 늘어난다


숫자로 보면 이해가 빠르다. `batch=16` 은 16개를 한 번에 GPU 에 올려 한 번 갱신한다. `batch=1, accumulation=16` 은 1개씩 16번 올려 그래디언트를 더해 두고 마지막에 한 번 갱신한다. **갱신 1회가 반영하는 샘플 수(유효 배치 16)는 같고, 동시에 GPU 에 올라가는 양은 1/16 이다.** 대신 순전파·역전파를 16번 하므로 시간이 늘어난다.


따라서 24GB 에서는 `batch_size` 를 낮추고 `grad_accumulation_steps` 를 올려 유효 배치를 맞추는 조합을 찾는 것이 실습 3 의 일이다. **메모리는 batch 가, 시간은 유효 배치가 결정한다.**


### 3. 4-bit 학습 경로는 있지만 쓰지 않는다


upstream 학습 스크립트에는 4-bit 양자화 학습 옵션이 있다. 켜면 base 가 2바이트에서 0.5바이트급으로 내려가 12GB 안에 들어올 여지가 생긴다. 즉 **로컬 4070 으로도 학습이 가능해질 수 있다.** 그런데 이번 Phase 에서는 쓰지 않는다.


| 이유 | 설명 |
|---|---|
| upstream 경고 | 스크립트 자체가 "메모리는 줄지만 성능을 해친다" 고 명시한다 |
| **교란 변인** | 산출물이 before/after 정량 분석이다. 학습 경로가 비표준이면 "성공률이 안 올랐다" 의 원인이 데이터인지 4-bit 학습인지 분리되지 않는다 |
| 비용 대비 | 24GB 클라우드 인스턴스 비용은 1사이클 기준 미미하다. 위 리스크를 감수해 아낄 금액이 아니다 |


두 번째 줄이 핵심이다. week6 의 "배제된 후보" 표를 떠올리면 이해가 쉽다. 4-bit 학습을 쓰면 그 표에 "4-bit 학습 때문일 수 있다" 는 행이 추가되고, 그 행을 배제하려면 표준 경로로 한 번 더 학습해 비교해야 한다. **결국 더 비싸진다.**


이것이 "RunPod 을 쓰는 이유" 의 정확한 서술이다 — 로컬 PC 를 못 만져서가 아니라 **표준 경로로 돌려 변인을 줄이기 위해서**다. 물리 접근 조건이 바뀌어도 이 판단은 유지된다.


### 4. `max_steps` 기본값은 우리 예산의 규모가 아니다


학습 스크립트의 기본 스텝 수는 20만 스텝 규모다. 사전학습급 실험을 전제한 값이므로, 그대로 실행하면 **예산을 초과하기 전에 끝나지 않는다.** 시간당 요금이 붙는 클라우드에서 이것은 곧 "언제 끊어야 할지 모르는 상태로 돈이 새는" 상황이다.


우리는 반대 방향으로 정한다.


```mermaid
flowchart LR
    A["예산<br/>시간 · 비용"] --> B["probe 로 측정<br/>스텝당 초"]
    B --> C["가능한<br/>총 스텝 수"]
    C --> D["max_steps<br/>명시 지정"]
```


probe 로 스텝당 시간을 재고 거기서 역산한다 (실습 3). 예를 들어 스텝당 3초이고 허용 시간이 2시간이면 2400 스텝이 상한이고, 여유를 빼 2000 스텝으로 지정하는 식이다. 이 값은 week1 §6 에서 데이터 규모를 정할 때 세운 "컴퓨트 예산" 방향과 같은 계산이며, 여기서 실측으로 채워진다.


### 5. 체크포인트는 선택이 아니다


Community Cloud 인스턴스는 회수될 수 있다. 개인이 제공한 GPU 를 싸게 빌려 쓰는 등급이므로, 제공자가 회수하면 실행 중인 pod 가 사라진다. 학습이 몇 시간 단위면 회수 확률은 무시할 수 없다.


| 수단 | 역할 |
|---|---|
| network volume | pod 를 멈춰도 남는 저장 공간. 체크포인트를 여기에 둔다 |
| 주기 저장 (`save_steps`) | 회수 시점 이후의 진행만 잃는다 |
| 최신만 덮어쓰기 vs 시점별 보관 | 덮어쓰기는 용량이 작고, 시점별 보관은 되돌릴 수 있다 |


첫 줄이 특히 중요하다. pod 의 기본 디스크는 pod 와 함께 사라진다. 즉 **체크포인트를 pod 안에만 저장하면 회수 시 학습 결과가 통째로 없어진다.** volume 은 pod 와 분리된 저장소라 남는다.


마지막 항목은 트레이드오프다. 학습이 발산했을 때 (loss 가 치솟는 경우) 이전 체크포인트로 돌아가려면 시점별 보관이 필요하고, 용량이 부담이면 덮어쓰기를 쓴다. **어느 쪽을 골랐는지 기록**해야 실습 5 의 복구 리허설이 성립한다.


그리고 유휴 과금이 있다. 학습이 끝나 아무것도 하지 않는 pod 도 켜져 있으면 요금이 붙는다. 작업이 끝나면 pod 를 멈춘다 — volume 은 남는다.


### 6. 학습 통계가 함께 저장된다 — 추론의 `unnorm_key` 가 여기서 생긴다


학습 스크립트는 데이터셋 통계를 실행 디렉터리에 함께 저장한다. 이것이 week2 §4 의 오른쪽 갈래다.

```mermaid
flowchart LR
    A["week2 RLDS<br/>원시 단위 라벨"] --> B["학습 중<br/>통계로 정규화"]
    B --> C["통계가 실행 디렉터리에<br/>함께 저장"]
    C --> D["Section 3 추론<br/>unnorm_key = 내 데이터셋"]
```


**따라서 체크포인트만 회수하고 통계 파일을 빠뜨리면 fine-tuned 모델을 쓸 수 없다.** 이유를 다시 정리하면 이렇다. 모델은 정규화된 값을 내놓도록 학습됐고, 그것을 미터·라디안으로 되돌리려면 학습에 쓴 통계가 필요하다. week0 에서 남의 로봇 통계를 빌려 썼던 자리에 이제 내 통계가 들어가야 하는데, 그 통계가 없으면 역정규화 기준이 사라진다. 회수 목록에 반드시 넣는다 (실습 4).


통계 파일은 수십 KB 급이라 15GB 가중치 옆에서 눈에 띄지 않는다. **작아서 빠뜨린다** 는 것이 이 함정의 성질이다.


### 7. 체크포인트 저장 시 어댑터가 이미 머지된다


학습 스크립트는 체크포인트를 저장할 때 LoRA 어댑터를 base 에 머지해 저장한다. 머지는 "얼려 둔 원래 가중치에 학습한 보조 행렬을 합쳐 하나의 모델로 만드는" 작업이다. 즉 **week4 의 "머지" 작업 상당 부분이 여기서 끝난다.**


week4 에 남는 것은 머지된 가중치를 로컬로 내리고 **4-bit 양자화 + 호환성 검증**을 하는 일이다. 다만 어댑터 원본도 함께 보관하는 편이 낫다 — rank 를 바꿔 비교하거나 머지를 다시 하고 싶을 때 필요하다. 어댑터는 수십 MB 라 보관 비용이 사실상 없다.


### 8. loss 가 내려가는 것은 통과 기준이 아니다


week2 §8 에서 본 조용한 실패들은 loss 를 정상적으로 내려가게 만든다. 라벨이 일관되게 틀려 있으면 모델은 그 틀린 라벨을 잘 맞추게 되고, loss 는 예쁘게 떨어진다. loss 는 "모델이 준 정답에 가까워지고 있는가" 만 보므로, **정답 자체가 틀렸는지는 알려주지 않는다.**


이번 주의 통과 기준은 따라서 loss 곡선이 아니다.


| 통과 기준 | 확인 방법 |
|---|---|
| 1사이클 완주 | 지정한 스텝까지 도달하고 최종 체크포인트가 남았다 |
| 실측 기록 | 스텝당 시간, 총 시간, 비용, VRAM 피크 |
| 복구 가능 | 체크포인트에서 재개해 학습이 이어진다 (실습 5) |
| 회수 목록 완비 | 머지 가중치 + 어댑터 + **통계 파일** + 학습 설정 |


성공률이 올랐는지는 Section 3 의 eval 이 답한다. 이번 주가 답할 질문이 아니다.

## 이번 주 핵심 요약


1. **바닥은 frozen bf16 base 약 15GB** — 옵티마이저가 아니다. 그래서 24GB 급이 필요하다.
2. **batch 는 메모리를, 유효 배치는 시간을 결정한다** — grad accumulation 으로 둘을 분리한다.
3. **4-bit 학습은 안 쓴다** — 교란 변인을 만들지 않기 위해서다. 비용 문제가 아니다.
4. **`max_steps` 는 예산에서 역산한다** — 기본값은 우리 규모가 아니다.
5. **통계 파일도 회수 대상이다** — 없으면 fine-tuned 모델을 추론에 못 쓴다.
6. **loss 곡선은 통과 기준이 아니다** — 완주 · 실측 · 복구 · 회수 목록이 기준이다.
